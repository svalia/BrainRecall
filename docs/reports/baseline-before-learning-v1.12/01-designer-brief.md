# BrainRecall — ТЗ для ИИ-дизайнера

Версия 1.11 · 14 ноября 2026 · Языки интерфейса MVP: русский и английский; локализация во всех контурах с первого релиза.

## 1. Задача и результат работы

Спроектировать Telegram Mini App, которое помогает превращать материалы в сохраняемые знания, практиковать их применение и внедрять выбранные привычки. Результат: редактируемые макеты, библиотека компонентов, кликабельные сценарии, состояния и спецификация поведения для разработки. Это задание на проектирование; программирование и публикация приложения в него не входят.

Название продукта — BrainRecall. Источник концепции: `../../Knowledge_Habits_Product.md`. При расхождении цен использовать это ТЗ: Старт 499 Stars, Про 1 099 Stars. Оригинальные 299/799 — предыдущая гипотеза. Технические контракты — `02-development-spec.md`. Геймификация из раздела 7.1 обязательна для MVP; дополнительные платные механики вне этого объёма не добавлять.

## 2. Идея, аудитория и целевой результат

Пользователь читает книги, учится, осваивает профессиональные материалы и часто забывает прочитанное либо не узнаёт ситуацию, в которой оно пригодится. Он может вручную создать материал для повторений или загрузить источник, получить предложения ИИ, проверить их и начать короткие занятия. Параллельно он выбирает конкретные действия для жизни и настраивает привычки.

Основная job story: «Когда я узнал что-то полезное, я хочу сохранить смысл, потренироваться вспоминать и применять его, чтобы воспользоваться этим в подходящей ситуации после длительного перерыва».

Вторая job story: «Когда я хочу изменить поведение, я хочу связать небольшое действие с понятным сигналом и отслеживать выполнение, чтобы регулярно возвращаться к нему».

Основной контекст — телефон, короткая сессия 5–15 минут, ограниченное внимание. Пользователь знает Telegram, но может не знать терминов интервального обучения. Не требовать регистрации с паролем. Не обещать «автопилот», вечное запоминание, привычку за фиксированное число дней или доказанную эффективность самого приложения.

Результат обучения — самостоятельное воспроизведение после перерыва и применение в новом примере. Результат привычки — выполнение действия при выбранном сигнале. Серии показывают регулярность, а не освоение.

## 3. Объём MVP и продуктовые правила

Включить ручное создание знаний; темы; импорт текста и TXT/MD/PDF с текстовым слоем/DOCX/EPUB; проверку предложений ИИ; сохранённые упражнения; адаптивные повторения; свободные ответы с опциональной ИИ-проверкой; привычки; напоминания; прогресс; Free, триал и оплату Stars; экспорт и удаление данных.

Не включать OCR, фото страниц, аудио, голос, общий чат с ИИ, публичные сообщества, рейтинги, маркетплейс курсов, пакеты дополнительных квот и годовые тарифы. Если PDF — скан, объяснить ограничение и предложить вставить текст.

Знание содержит вопрос/смысл, ответ, условия применения и при наличии исходный фрагмент. Факт, мнение автора и гипотеза имеют разные подписи. ИИ предлагает; пользователь выбирает. Оригинал и задания доступны после исчерпания квот.

Тема — область знаний, материал — источник, элемент знания — единица повторения, упражнение — способ проверить элемент. Привычка — отдельное действие, которое можно связать с темой/знанием. Не смешивать эти сущности в одном плоском списке.

## 4. Информационная архитектура

Пять нижних разделов: **Сегодня · Знания · Привычки · Материалы · Прогресс**. Профиль/настройки — отдельный вход в шапке каждого корневого раздела, ниже нативных контролов. На формах и во время занятия нижнюю навигацию скрывать; после выхода возвращать её без изменения состояния списков.

Иерархия: Знания → тема → элемент → редактирование; Привычки → привычка → редактирование/отметка; Материалы → материал → просмотр источника/черновики импорта; Прогресс → детализация; Настройки → уведомления/тариф/данные/помощь.

У каждого дочернего экрана один определённый родитель. Переходы между разделами задают контекстную кнопку «Открыть тему» и не меняют смысл нативного «Назад». Источник из занятия — временный просмотр, закрывающийся обратно в то же задание. Платёж — системная поверхность Telegram, а не нарисованный собственный кошелёк.

## 5. Сквозные пользовательские сценарии

### 5.1. Первый запуск без ИИ

Бот /start → открыть приложение → D00 → D01 → выбрать «Добавить вручную» → D06 → D07 → D09 → D10 → D11 → D12 → D13 → D03. Пользователь создаёт тему, один вопрос и ответ, пробует повторение. Триал не запускается, оплата не требуется. Напоминания предложить после первого полезного результата; разрешено отказаться.

### 5.2. Первый импорт с ИИ

D01 «Попробовать ИИ бесплатно» / D03 → D06 с выбранным способом ИИ и выбором темы → D15 → D16 → D17 → D18 → D08 → D10. До операции объяснить передачу текста ИИ, объём, расход и начало триала. После обработки дать проверить предложения, снять лишние и исправить ошибки. Только принятые элементы активируются для обучения. Если нужного места в плане нет, предложить уменьшить выбор или выбрать тариф; черновик сохраняется. Покупка прямо с лендинга: D01 → D27 → D28 → после подтверждённой оплаты D06 с выбором первого материала; возвращать покупателя к созданию результата, а не на рекламную страницу.

### 5.3. Ежедневное возвращение

Напоминание бота или обычный вход → D03 → продолжить незавершённую/начать новую сессию D10 → D11/D12 → D13 → D03 → отметить привычку D22. При входе из уведомления открыть целевой экран с определённым родителем, а не цепочку случайных прошлых страниц.

### 5.4. Новая привычка

D19 → D20 → вручную заполнить план → D21 → D22 → D03. Опционально на D20 запросить помощь ИИ: D23 → пользователь принимает/редактирует план → D20 → сохраняет. План ИИ сам не запускает привычку.

### 5.5. Квота и оплата

D16/D12/D23 → D30 при недостатке квоты → D27 → нативная оплата → D28 → после серверного подтверждения вернуть к подготовленному действию. Не запускать ИИ автоматически после покупки: повторно подтвердить расход. Отмена оплаты сохраняет текст и выбор.

### 5.6. Окончание доступа

Истёк платный период/триал → уведомление в интерфейсе → D29 → выбрать активные темы, знания и привычки в пределах Free. Остальное доступно для чтения и экспорта. При отсутствии выбора ничего не удалять и не назначать новые повторения сверх лимита. Оплата доступна, но не блокирует выгрузку данных.

### 5.7. Ошибка и возврат

Закрыл приложение посреди занятия → повторное открытие → D03 «Продолжить». Ошибка импорта → D17 с сохранённым источником и безопасным повтором. Нет сети → показать последнее доступное состояние и действие восстановления; не утверждать, что ответ или платёж сохранён. Ошибка ИИ-проверки → самопроверка без дополнительной оплаты за неудачу сервиса.

## 7. Обучение и привычки: как показать логику

В занятии чередовать припоминание, объяснение, выбор способа и применение. Варианты ответа — один из форматов, не универсальная замена припоминания. Не раскрывать ответ до попытки или явного запроса пользователя. Сложные формулы должны переноситься/прокручиваться внутри блока, а не раздвигать весь экран.

Самопроверка всегда доступна без ИИ: показать эталон и дать честную оценку. При проверке ИИ показывать происхождение оценки и возможность сообщить об ошибке. Дополнительные объяснения и новые кейсы стоят отдельную квоту; повторный показ сохранённого разбора бесплатен.

Общая серия, серии тем и привычек, нейтральные дни, пропуски и достижения рассчитываются по единому правилу раздела 7.1. Не рисовать «освоено» за серию или открытие приложения.

### 7.1. Обязательная геймификация MVP — решение владельца

Этот раздел явно разрешает и требует общую серию, серии объектов, личные рекорды, календарь, значки достижений, празднование и возврат после пропуска. Дизайнеру не нужно отдельно согласовывать их добавление. Цель — помочь возвращаться и замечать регулярность, в том числе хотеть выполнить план, чтобы сохранить ударный режим. Очки/XP, лиги, публичные рейтинги, персонажи, внутренняя валюта и покупка восстановления уже сброшенной серии не входят в MVP. Бесплатные механики доступны на Free, Trial и платных тарифах без расхода ИИ. Бесплатная выдача и отдельная покупка защиты за Telegram Stars разрешены разделом 7.2; прежний запрет платных заморозок отменён.

**Единое определение общей серии:** число зачтённых дней, в которые выполнен весь зафиксированный посильный дневной план. Нейтральные дни между ними сохраняют цепочку, но не увеличивают счётчик. Поэтому подпись «зачтённых дней в серии», а не обещание активности каждый календарный день. Не считать достаточным выполнение одного задания, если в плане остались другие обязательные действия.

Дневной план включает посильную очередь повторений по темам и запланированные на этот день привычки. Просроченные знания сверх дневного бюджета остаются видимым остатком и не превращаются в бесконечное условие серии. Необязательные новые знания/кейсы не мешают завершить план. Человек заранее видит объём: «Повторения 6/8 · Привычки 1/2» и что осталось для зачёта. Ошибочные ответы тоже являются выполненной практикой: план не требует 100% правильности. Выполнение привычки в минимальной версии достаточно.

| Состояние дня | Общая серия | Как показывать |
|---|---|---|
| Все обязательные части выполнены; есть реальное учебное действие/выполнение привычки | +1 один раз за локальный день | «План выполнен», заполненная отметка; текущая серия и рекорд |
| Часть плана ещё не выполнена, день продолжается | Пока без +1, предыдущая серия сохраняется до конца дня | «Осталось…», нейтральный прогресс без преждевременного сброса |
| План был, день закончился с невыполненными частями и защиты нет | Цепочка прерывается, текущая серия 0 до нового зачёта | Пропуск; история и рекорд сохраняются; D37 при возвращении |
| Нет заданий/плановая пауза; все возможности привычек действительно не возникли | Без +1 и без разрыва | «День без плана — серия сохранена», отдельный нейтральный знак |
| Нет обязательного плана, но завершена добровольная реальная сессия или выполнена запланированная/добавленная на сегодня привычка | +1 один раз | «Практика выполнена»; не выдавать просмотр демо за практику |

Пауза не закрывает пропуски задним числом. Изменение настроек не удаляет уже начатый дневной план ради спасения серии. Исключение — явное исправление ошибочной отметки привычки, которое честно пересчитывает статистику. Техническая логика снимка плана и времени — в ТЗ разработчика.

**Серии объектов:** тема засчитывается за выполнение её части плана, привычка — за minimum/full на запланированную возможность. В общей сессии темы считаются независимо. День без практики данной темы, пауза привычки и отсутствие сигнала нейтральны. Подписи различаются: у темы «зачтённых дней», у привычки «выполнений подряд по плану»; привычка 3 раза в неделю не требует ежедневных отметок. Общая серия может прерваться, даже если серия отдельной выполненной темы продолжается. В календаре показывать дату и тип события, а не один зелёный цвет на всё.

**Достижения:** пороги 1, 3, 7, 14, 30, 60, 100, 180 и 365 для общей серии и серий объектов. У каждой отметки простой значок и конкретное название: «30 зачтённых дней» или «30 выполнений по плану», а не «память прокачана на 30%». Достижение за порог выдаётся один раз на объект, новый личный рекорд показывается отдельно. После разрыва серии уже полученные достижения сохраняются; заведомо ошибочные данные могут корректироваться. Не повторять празднование тех же 7/30 при каждом повторном открытии.

**Празднование D38:** 1–2 секунды необязательной анимации, сразу доступна кнопка продолжения; success haptic один раз при действии в активном приложении. Без автозвука. При reduced motion/выключенных эффектах — статичный текст. Если один шаг завершил несколько серий/порогов, одна поверхность с кратким итогом и ссылкой D36, не очередь из пяти модалок. Успех сессии и достижение не дают два одновременных haptic.

**Возврат D37:** после пропуска показывать один раз при ближайшем входе, а не при каждой вкладке; множественные пропуски объединять в один итог. Нельзя принуждать к признанию неудачи и скрывать обычную навигацию. До наступления конца локального дня D37 не показывается. После нового выполненного дня текущая серия начинается с 1; прежний рекорд остаётся. Если пользователь уже вернулся к практике через deeplink, не прерывать её экраном пропуска — показать мягкий итог позже.

**Где видна геймификация:** D03 — общая серия, план и ссылка D36; D08/D21 — серии объектов; D13/D22 — непосредственный результат; D24/D25 — календарь и рекорды; D36 — подробности/значки; D37/D38 — возврат/празднование, D39 — защита серии. В D26 добавить «Эффекты достижений»: анимацию можно отключить; цифры и результаты сохраняются. Все тексты локализованы, серии не меняют доступ/тариф и не означают освоение знаний.

**Примеры для макетов:** пн выполнен → серия 1; вт без плана → остаётся 1; ср выполнен → 2; чт часть плана не завершена к концу дня → 0; пт выполнен → 1, рекорд 2. Второй пример: привычка пн/ср/пт — три выполнения, а не пять календарных дней. Третий: один ответ завершает тему и общий план на пороге 30 — одно объединённое празднование.

### 7.2. Заморозки: бесплатная выдача, предел запаса и покупка

Это актуальное решение владельца: добавить защиту на один день и на неделю, бесплатную выдачу за регулярную практику и покупку за Stars. Заморозка сохраняет текущие общую и объектные серии на защищённую дату, но не увеличивает их и не считается выполненным планом/усвоением. Дни без плана по-прежнему нейтральны бесплатно.

| Правило | Решение MVP |
|---|---|
| Стартовая помощь | После первого реально зачтённого дня выдать одну бесплатную однодневную заморозку один раз на аккаунт |
| Регулярная выдача | Одна бесплатная заморозка за каждые 7 реально зачтённых дней общей серии, суммарно за всё время. Дни не обязательно подряд: сброс серии не отнимает прогресс к следующей награде |
| Максимум в запасе | Всего **2 однодневные заморозки на аккаунт**, включая бесплатные и купленные; не по две на тему |
| Если запас полон | За очередные 7 дней новая не выдаётся и не откладывается. После достижения порога начинается новый цикл из 7 зачтённых дней; скрытой очереди накопленных наград нет |
| Прогресс | Показывать «До бесплатной заморозки: 4/7 зачтённых дней»; при 2/2 — «Запас полон. Следующая награда не накопится сверх лимита» |
| Автоприменение | Пользователь явно включает. На границе дня с невыполненным планом расходуется одна уже имеющаяся защита; без согласия Stars автоматически не списываются |
| Покупка дня | Разовая оплата Stars пополняет запас на 1, только если есть место. Показывать источник/историю; платные единицы не сгорают по сроку |
| Покупка недели | Выбрать интервал 7 календарных дней со стартом завтра или позже, не далее 30 дней вперёд; одна активная/запланированная неделя, без складирования купонов и перекрытия интервалов |
| Ограничение использования | Максимум **7 защищённых дат за скользящие 30 локальных дней** на аккаунт, суммарно однодневной и недельной защитой. Будущая неделя резервирует все 7 дат для этого лимита; перед оплатой показать доступность |
| Что не приносит награду | Замороженный/нейтральный день, демо, покупка и вход в приложение не приближают бесплатную выдачу |

Одна однодневная единица защищает все существовавшие цепочки аккаунта, которым нужен пропуск именно на эту дату; не списывать отдельно за каждую тему/привычку. Применять лишь при наличии серии >0, которую требуется сохранить. Если всё выполнено либо нет пропуска/серии, единица не расходуется. Недельная защита действует на выбранные даты, а не даёт семь единиц в запас. Внутри неё не списываются однодневные. Если пользователь занимается в защищённый день, он получает обычный earned; оплаченный календарный интервал не продлевается и не переносится. Это видно до оплаты. План и долг не исчезают: защита сохраняет серию, не выполняет задания за человека.

Платная неделя доступна только при существующей сохраняемой серии и свободном лимите. Недельный план нельзя складывать в бесконечный запас: одновременно только один интервал; новый должен пройти проверку лимита. Покупка защиты не восстанавливает уже случившийся пропуск и не спасает день, закончившийся до подтверждённой покупки. Бесплатная плановая пауза тем/привычек остаётся; объяснять её как бесплатный вариант отдыха, не скрывать ради продажи защиты.

В D03: серия, остаток плана, иконка защиты/запас 0–2 и вход в D39. В D36: календарь с отдельным frozen-символом и легендой, рекорд, ссылка «Защитить серию». В D39: условия выдачи, цикл 7 дней, лимиты, переключатель автоматического использования, остаток/история, цена дня и выбранной недели из серверного каталога. Цены заморозок — отдельные настраиваемые товары, не включены автоматически в 499/1 099 Stars; не придумывать фиксированную цену в макетах, связать placeholder с price config.

Состояния D39: 0/2, 1/2, 2/2; бесплатная награда получена/не выдана при полном запасе; автоприменение on/off; неделя активна/запланирована; исчерпан лимит 7/30; pending/cancelled/failed/paid. При 2/2 покупка дня недоступна с объяснением. Если отказала покупка, запас и серия не меняются. После защиты: «Вчера заморозка сохранила серию. Осталась 1 из 2». После недели: «Серия сохранена. Вернёмся с небольшого шага?» — без наказания. Празднование бесплатной награды объединять с D38, не показывать отдельные модалки подряд. Все новые строки локализовать.

Пример против накопления: запас 2/2, пользователь заработал ещё 21 день — запас остаётся 2, нет трёх наград «на потом». После использования одной баланс 1/2, дальше выдача только при следующем реальном достижении очередного семидневного порога. Замороженная неделя не даёт ни прироста серии, ни бесплатной заморозки.

|---|---:|---:|---:|---:|
| Цена | 0 | 0 | 499 Stars | 1 099 Stars |

Ручное создание, сохранённые упражнения, алгоритмическое расписание и напоминания есть во всех режимах. Триал начинается только после явного подтверждения первой ИИ-операции; автоматической оплаты после него нет. Лимиты общие на аккаунт. Один материал — до 100 000 токенов извлечённого текста; нет округления каждого короткого файла до 10 000. Фактическое число созданных элементов не обещать заранее.

Рабочее решение для запуска: платные тарифы с явным автопродлением через Stars раз в 30 дней; показать это до оплаты и дать простое отключение. Смена тарифа — со следующего периода, без немедленного двойного списания и без пересчёта остатка. Старое продление останавливается, в конце периода пользователь подтверждает новый invoice на выбранный тариф; без новой оплаты включается Free. Не обещать автоматическую смену цены без подтверждения. Запрос смены можно отменить до начала следующего периода с восстановлением старого продления после явного согласия. Подробный механизм — в ТЗ разработчика. Рубли и доллары из экономики разработчика не показывать пользователю как розничную цену.

## 9. Общие требования

### 9.1. Нативные контролы Telegram и безопасные зоны

Все экраны, sheets, липкие шапки и кнопки должны оставлять место системному интерфейсу. Нативные Назад/Закрыть слева, меню и сворачивание справа рисовать только как отдельный слой окружения в макете; не реализовывать дубли внутри страницы.

Единого официального отступа «56/80/100 px на всех телефонах» нет. Источник размеров — `safeAreaInset` и `contentSafeAreaInset` / соответствующие CSS-переменные Telegram. Первое относится к устройству, второе — к контролам Telegram. Размеры динамические; спецификация реализации — раздел 3 ТЗ разработчика. [Официальное описание](https://core.telegram.org/bots/webapps#safeareainset), [контентная область](https://core.telegram.org/bots/webapps#contentsafeareainset).

Для макета: внешний слой «Device safe area», внутри «Telegram controls safe area», затем контент с дополнительным дизайнерским зазором **12 px сверху и 16 px по бокам**. Это наши отступы после безопасной области, а не размеры Telegram. Показать вариант без fullscreen, fullscreen с вырезом и маленький экран. Не фиксировать высоту нативных зон как продуктовую константу. Фон может продолжаться под контролами; текст и действия — нет. Нижняя навигация и CTA также учитывают безопасный низ; клавиатура не перекрывает ввод и продолжение.

#### 9.1.1. Глобальный Grabber / Drag Handle для сворачивания Mini App

На всех экранах D00–D39 предусмотреть единый **граббер** — короткую горизонтальную полоску, показывающую, что приложение можно потянуть вниз и свернуть средствами Telegram. Это элемент общей оболочки, не отдельного экрана и не системный Home Indicator. При смене раздела он не исчезает, не прыгает и не уезжает вместе с прокручиваемым содержимым. На системных поверхностях Telegram (invoice/нативный диалог) приложение не рисует свой слой поверх системного.

Визуальный ориентир: **38×5 CSS px**, скругление **99 px**, цвет **#48484A в светлой теме**; для тёмной темы — контрастный нейтральный токен. Полоска центрирована по горизонтали между нативными Назад/Закрыть слева и шевроном/меню справа. На поддерживаемом fullscreen-клиенте центр по вертикали рассчитывается относительно верха WebView как `safeAreaInset.top + contentSafeAreaInset.top / 2`. Это ориентир компоновки, который проверяется на реальных клиентах, а не официальная координата кнопок Telegram. При нулевой/недоступной области не рисовать полоску в статус-баре или поверх выреза.

При необходимости под полоской — спокойная верхняя градиентная подложка в цвет темы, согласованная с нативным header. Подложка не должна скрывать, подменять или перехватывать нативные кнопки. Сам граббер декоративный, без собственного клика и без haptic. Нельзя обещать жест, который на данном клиенте не работает.

Смысл жеста: **свернуть текущее Mini App в панель Telegram и сохранить состояние**, а не закрыть приложение, перейти назад или открыть чаты нарисованного интерфейса. Пользовательский скриншот свёрнутой панели — только референс результата Telegram; нижнюю панель, список чатов и управление ими внутри BrainRecall не проектировать.

Обязательные варианты макета: fullscreen с граббером в строке контролов; обычный режим, где нативный header находится за пределами DOM; fallback старого клиента/Desktop. Если точная нативная строка недоступна WebView, не рисовать фальшивую копию header ради полоски: использовать нативный handle клиента, если он есть, либо расположить подсказку на доступной верхней границе приложения без дублирования. Этот платформенный fallback — единственное исключение из требования одной и той же физической позиции; цель и предсказуемость жеста сохраняются.

Приёмка: полоска не перекрывает нативное управление, видна в светлой/тёмной теме, остаётся на месте при прокрутке и переходах; свайп из доступной нативной верхней зоны сворачивает поддерживаемый клиент, после возврата восстановлены экран, scroll и черновики. Различать глобальный граббер Mini App и локальные handles внутренних bottom sheets: локальный жест управляет своим sheet, не должен внезапно закрывать приложение.

### 9.2. Тактильный отклик

Использовать официальный `Telegram.WebApp.HapticFeedback`: `impactOccurred('light')` для активной кнопки, `selectionChanged()` для изменения выбора, `notificationOccurred('success'|'warning'|'error')` для результата. [API](https://core.telegram.org/bots/webapps#hapticfeedback).

В макетах отметить места отклика. Один жест — один логический сигнал: если сразу показывается успех, не накладывать на него ещё удар. Нет вибрации на скролл, ввод букв, неактивную кнопку и фоновые события. Есть выключатель в настройках. На устройствах без поддержки интерфейс сохраняет визуальную обратную связь.

### 9.3. Иерархический Назад

Нативная кнопка должна вести к родителю экрана, не к последней записи browser history. На корнях пяти вкладок скрыта; остаётся нативное закрытие Telegram. Сначала закрывается модальный слой, затем выполняется переход к родителю. В мастере редактирования предыдущий шаг является родителем шага. При выходе с несохранёнными изменениями — сохранить черновик или подтвердить отказ. На занятии Назад → подтверждение паузы → Сегодня; прогресс сохраняется. [Нативная кнопка](https://core.telegram.org/bots/webapps#backbutton).

### 9.4. Портретная ориентация

Пользователь подтвердил: **основной режим всегда вертикальный**. `lockOrientation()` фиксирует текущую ориентацию; вызвать его после подтверждения портретного положения. Если открыли горизонтально, показать компактное предложение повернуть телефон, затем зафиксировать портрет. API не выбирает портрет аргументом. [Официальный метод](https://core.telegram.org/bots/webapps#initializing-mini-apps).

На неподдерживаемом клиенте — адаптивная рабочая компоновка; не поворачивать весь HTML через transform и не блокировать доступ к данным. На desktop не просить физически перевернуть монитор: показывать центрированную колонку. Дизайнер должен подготовить эти состояния.

### 9.5. Визуальный язык, доступность и доверие

Спокойный взрослый интерфейс, ясная типографика, один главный CTA на экран. Порядок внимания: что нужно сделать → действие → пояснение/снятие сомнений. Ориентир сетки 4/8 px; текст от 16 px, нажатия от 44×44 CSS px, контраст основного текста от 4,5:1. Светлая/тёмная темы; читаемость при увеличении шрифта 200%; focus и screen reader labels; reduced motion. Цвет всегда дублировать подписью/символом.

Не копировать Duolingo: взять идею короткой сессии и серий, но не персонажей, интерфейс и принуждение. Не использовать ложные таймеры, скрытые платные опции, стыдящие отказы и обещания точного результата. Ошибки — простым языком с конкретным следующим действием. Технические токены спрятать в пояснение там, где они не нужны для выбора; перед расходом показать понятный объём и точный счётчик.

### 9.6. Локализация (i18n): Telegram Bot + Mini App + Web / API / MCP

Актуальная редакция требований владельца от 14.11.2026. Полностью заменяет прежний текст этого раздела, включая старые дополнения о гибридной локализации и правила Homestead Prime. Первый релиз BrainRecall включает полные ru/en. Ниже приведён новый единый контракт; отдельной альтернативной схемы profile.language/ui_locale больше нет.

#### 1. Единый источник правды (Single Source of Truth)
- Все переводы хранятся в структурированных JSON-каталогах на бэкенде: `locales/<lang>.json` (например, `ru.json`, `en.json`).
- Структура ключей единая и иерархическая для всех слоёв продукта:
  - `meta.*` — код языка (`code`), название языка (`label`), направление текста (`dir`).
  - `bot.*` — все сообщения, кнопки (`InlineKeyboard` / `ReplyKeyboard`), команды, алерты и ошибки Telegram-бота.
  - `miniapp.*` — все экраны, вкладки, модалки/шторки, плейсхолдеры, aria-атрибуты, тосты и ошибки валидации Mini App.
  - `api.*` / `mcp.*` — пользовательские тексты ошибок API, описания инструментов/ресурсов и системные инструкции для внешних клиентов.
- Строгий паритет ключей: набор ключей во всех `locales/*.json` должен на 100% совпадать.
- Подстановка переменных в строках выполняется через именованные плейсхолдеры `{var_name}` (одинаковый формат на бэкенде и фронтенде).

#### 2. Приоритет определения языка и флаг ручного выбора (`locale_override`)
У каждого пользователя в БД хранятся два поля:
- `locale: str` (нормализованный код языка, например `"ru"` или `"en"`, с дефолтным fallback).
- `locale_override: bool` (по умолчанию `False` — менял ли пользователь язык вручную в настройках).

Правила синхронизации языка:
1. **Первый вход (в бота или Mini App):**
   - Берётся `language_code` из объекта `from` апдейта Telegram или `initDataUnsafe.user.language_code` в WebApp.
   - Нормализуется по базовому IETF-тегу (`"en-US"` -> `"en"`, `"ru-RU"` -> `"ru"`; неподдерживаемые языки -> дефолтный язык).
   - Сохраняется в `user.locale` при `locale_override = False`.
2. **Повторные запросы от Telegram:**
   - Если `user.locale_override == False`, `user.locale` автоматически обновляется при смене языка клиента Telegram.
   - Если `user.locale_override == True`, язык из клиента Telegram **не перезаписывает** выбор пользователя.
3. **Ручное переключение языка в настройках Mini App (или командой `/lang` в боте):**
   - Отправляет `PATCH /api/v1/settings` с `{ "locale": "<lang>" }`.
   - Бэкенд выставляет `user.locale = <lang>` и `user.locale_override = True`.
   - Выбор сразу применяется и в Mini App, и во всех последующих сообщениях бота, и во внешних интеграциях (API / MCP).

#### 3. Архитектура локализации в Telegram Mini App
- **Эндпоинт каталога:** `GET /api/v1/i18n?lang=<lang>` возвращает слитый с базовым языком каталог (чтобы при отсутствии ключа в переводе автоматически подставлялся дефолтный язык, а не сырой ключ).
- **Порядок инициализации (`bootstrap`):**
  1. До первого рендера UI определяется стартовый язык: `localStorage/CloudStorage ("locale")` -> `Telegram.WebApp.initDataUnsafe.user.language_code` -> дефолтный язык.
  2. Загружается каталог `/api/v1/i18n?lang=<initialLang>` (или берётся из кэша), разворачивается словарь строк и только после этого вызывается первый `render()`.
  3. После ответа `GET /api/v1/me` сверяется `me.user.locale`: если на сервере сохранён другой язык, догружается нужный каталог и UI перерисовывается.
- **Мгновенное переключение без перезагрузки:**
  - Переключатель языка (`RU / EN`) в настройках обновляет `state.locale`, кэширует выбор в `localStorage` / `Telegram.WebApp.CloudStorage`, подгружает словарь, синхронно вызывает `render()`, меняет `<html lang="...">` и отправляет `PATCH /api/v1/settings`.
- **Защита от типичных багов во фронтенде:**
  - Функция перевода `t(key, vars)` должна иметь зарезервированное имя: внутри рендер-функций и обработчиков событий **запрещено** называть локальные переменные `const t = ...` или параметры `(t) => ...`, чтобы не перекрывать `t()`.
  - Даты, время и числительные форматируются с учётом `state.locale` (`Intl.DateTimeFormat(state.locale === "en" ? "en-US" : "ru-RU", ...)`).

#### 4. Локализация Telegram-бота
- Все обработчики команд (`/start`, `/help`, `/settings` и др.), callback-кнопок и фоновых уведомлений получают `user.locale` и формируют тексты/кнопки только через `t("bot.*", user.locale, **vars)`.
- При смене языка в Mini App новые уведомления и карточки от бота сразу приходят на выбранном языке.
- Меню команд бота (`setMyCommands`) регистрируется отдельно для каждого поддерживаемого `language_code` (`ru`, `en`, и дефолтный без `language_code`).

#### 5. Гибридный флоу для лендинга, документации и внешних клиентов (MCP / CLI / Web)
Должны поддерживаться оба сценария входа пользователя:

##### Сценарий А — Пользователь сначала зашёл в бота или Mini App (Warm Start)
- Язык пользователя уже известен (`user.locale`).
- Генерируемые в боте и Mini App команды установки, промпты для ИИ-агентов и инструкции отдаются на языке `user.locale` (с явным параметром `?lang=<locale>` в ссылках на инструкции, например `https://.../install.md?lang=en`).
- Когда внешний клиент / MCP-сервер подключается по токену или коду привязки этого пользователя, сервер читает `owner.locale` и автоматически отдаёт описания инструментов (`tools/list`), ресурсы (`resources/list`), системные инструкции (`initialize`) и ответы/ошибки на языке владельца.

##### Сценарий Б — Холодный старт с лендинга, GitHub или маркетплейса до входа в бота (Cold Start)
- Публичные веб-страницы (`/`, `/guide`, `/install.md`, `/oauth/authorize`) определяют язык по приоритету:
  1. Явный query-параметр `?lang=en|ru` в URL;
  2. Сохранённый выбор `localStorage` в браузере + видимый переключатель `RU | EN` в шапке сайта;
  3. Заголовок `Accept-Language` браузера/клиента;
  4. Дефолтный язык (на международных площадках GitHub / npm / MCP-маркетплейсах базовые README и команды публикуются на английском или содержат `?lang=en`).
- Команда, скопированная с английской версии лендинга или из README на GitHub/npm, содержит `?lang=en`, поэтому агент сразу получает английский `install.md` и ведёт онбординг на английском ещё до привязки аккаунта Telegram.

#### 6. Автоматическая проверка перед деплоем (Checklist)
1. Скрипт проверки паритета ключей: все ключи из `ru.json` присутствуют в `en.json` и наоборот.
2. Скрипт проверки покрытия в коде: каждый вызов `t("...")` в коде бота и Mini App ссылается на существующий ключ в JSON-каталогах.
3. Проверка отсутствия захардкоженной кириллицы в UI-шаблонах и отсутствии перекрытия (`shadowing`) функции `t`.

#### Применение к BrainRecall и уточнения реализации

- Минимум две полные локали ru/en с первого релиза. DEFAULT_LOCALE задаётся централизованным конфигом (для основного приложения базовый ru); публичные GitHub/npm/MCP-материалы имеют английский базовый текст. Неподдерживаемый код нормализуется в поддерживаемый default, а не создаёт новую локаль произвольно. Дальнейшие локали добавляются валидным файлом и декларативными meta, без переписывания бизнес-логики.
- В профиле хранятся только canonical `locale` и `locale_override`; ответ `GET /api/v1/me` содержит `me.user.locale` и `me.user.locale_override`. Поля profile.language/ui_locale из прежней редакции не являются вторым источником. При миграции перенести старый явный выбор в locale_override=true, не обнулить preference существующего пользователя. Свойство аналитики языка также `locale`.
- Telegram language_code опционален. Сервер обновляет locale при override=false только из достоверного Telegram update/проверенного initData. Отсутствующее поле не сбрасывает уже сохранённый язык; при первом входе без поля используется default. initDataUnsafe годится лишь как предварительная клиентская подсказка, не для авторизации. На активном веб-сеансе Telegram может не прислать изменение языка мгновенно: синхронизация выполняется при следующем достоверном входе/update, не обещать несуществующее push-событие.
- D26 получает рабочий RU/EN-переключатель, /lang в боте — выбор того же свойства через общий settings service. Политика ручного выбора одинакова у бота и Mini App. Старый POST /api/profile заменён PATCH /api/v1/settings; публичный i18n использует query `lang`, не старый `locale`. Если понадобится совместимость старых клиентов, это временный явный alias с датой удаления, не два конкурирующих контракта.
- Переключение сначала загружает валидный каталог, затем атомарно обновляет state/cache/html lang (и dir из meta); во время загрузки остаётся читаемый текущий UI. Сохранение на сервере показывает saving/error/retry без ложного success; при неуспехе optimistic выбор явно pending или откатывается. CloudStorage асинхронен: не блокировать первый рендер бесконечно и не позволять позднему старому ответу перезаписать новый выбор. После me серверный выбор корректирует предварительный cache. Смена языка не теряет форму, сессию, timezone и не запускает LLM.
- Иерархия ключей строго meta/bot/miniapp/api/mcp, включая лендинг в miniapp либо отдельный согласованный раздел с паритетом во всех каталогах. Не сохранять старые независимые namespaces как второй набор переводов. В каждом meta различаются значения code/label/dir, но структура ключей совпадает. Именованные {var_name} и plural-контракт едины; проверяется также паритет имён параметров и типов, экранирование и безопасный rich text. t — зарезервировано для translator, lint запрещает shadowing.
- Строгий паритет и merged fallback не противоречат: CI не выпускает неполный пакет, runtime merge с базовой локалью защищает от повреждённого cache/несовместимой версии. t не показывает сырой ключ пользователю; отсутствующий в базовом каталоге ключ — ошибка разработки. Веб получает лишь разрешённую публичную проекцию каталога; секреты и приватные LLM system prompts не выдаются через /api/v1/i18n. Версия каталога, cache/ETag и защита от path traversal обязательны.
- Нативные имя/описания профиля и setMyCommands по языкам/default остаются отдельной витриной Telegram; локализуются описания команд, не сами /start и /lang. Подготовить RU/EN preview-медиа BotFather. Telegram выбирает эту витрину по своему языку: ручной locale нашего приложения сам по себе не меняет весь язык клиента Telegram.
- Для авторизованного внешнего API/MCP язык берётся из owner.locale; до авторизации публичный Web использует query → browser choice → Accept-Language → default. HTTP-сервер не может читать localStorage напрямую: браузер передаёт выбранную locale явным параметром/разрешённым механизмом; markdown/CLI-клиенты без browser storage используют query/Accept-Language/default. Недоверенный lang валидируется, не изменяет чужой профиль и не попадает в shell без безопасного формирования команд.
- MCP/CLI/GitHub/npm-пункты обязательны для соответствующих реально существующих/публикуемых компонентов, но не добавляют разработку нового MCP-сервера в MVP автоматически. При наличии MCP tools/list, resources/list и initialize instructions локализуются по owner.locale — прежнее правило «описания инструментов всегда English» отменено. Идентификаторы tools/параметров и JSON schemas остаются стабильными; при смене locale обновлять объявления/кеш в рамках возможностей MCP-клиента, при необходимости уведомлять о refresh/reconnect. Не обещать обновление уже кешированного списка в любом клиенте без его поддержки. Ответы и ошибки всегда на актуальном языке владельца.
- В макетах D00–D39 проверить реальные RU/EN строки, 200% шрифт и расширение перевода на 30–50%; переносы/размеры не должны ломать safe areas и CTA. В пользовательском контенте допустим исходный язык. Псевдолокаль — дополнительная QA-проверка, не замена настоящего en.
- Сдача: парные ru/en каталоги, аннотации ключей для дизайна, lint/parity/coverage отчёты, отсутствие hardcoded системной кириллицы (пользовательский контент/тестовые fixtures исключать обоснованно), проверки locale_override=false/true при смене Telegram language, bootstrap/cache/me, тостов/модалок/бота/дат, warm/cold внешнего входа. Реализованные экраны/сервисы должны ссылаться на этот единый контракт.

### 9.7. Удаление аккаунта и всех связанных данных

Если приложение создаёт или сохраняет учётную запись пользователя, в его профиле D26 обязателен явно видимый пункт **«Удалить аккаунт и данные»**. Это относится и к авторизации через Telegram, даже без отдельной формы регистрации. Пункт ведёт непосредственно в подтверждение D32, доступен на Free, после окончания тарифа и без обращения в поддержку. Экспорт рядом доступен как необязательное действие, не как условие удаления.

До подтверждения показать последствия: удалятся профиль BrainRecall, настройки, темы, материалы и файлы, знания/упражнения, ответы и история занятий, привычки, серии/достижения, запасы защиты и остальные связанные персональные данные; продление подписки останавливается. Удаление относится к аккаунту BrainRecall, не к Telegram-аккаунту. Активное пользовательское состояние не должно восстановиться при повторном входе. Минимально необходимый платёжный/обязательный аудит, резервные копии и внешняя обработка имеют отдельные объяснённые правила — не обещать мгновенно стереть то, что технически или юридически пока должно храниться.

Состояния: подтверждение → выполняется → завершено либо конкретная ошибка/повтор. На финальном подтверждении явно назвать необратимость, без стыда, скрытой отмены и покупки права удалить данные. Сроки и серверная очистка — раздел 13 ТЗ разработчика. После запроса не показывать маркетинговое удержание как обязательный шаг и не присылать обычные напоминания.

### 9.8. Обязательная продуктовая аналитика, независимая от сервиса

Аналитика должна быть внедрена с первого релиза. Сервис будет выбран позже; возможные назначения: Amplitude, Google Analytics 4, Яндекс Метрика, self-hosted PostHog, а также Metabase поверх собственной аналитической БД. В макетах и логике продукта не должно быть зависимости от конкретного поставщика.

Дизайнер сдаёт аннотации аналитики для ключевых экранов и действий: стабильный event key, точка отправки (просмотр/тап/подтверждённый результат), свойства, цель измерения и источник client/server. Общая схема событий/свойств пользователя едина для бота и Mini App. Имена событий и значения системных статусов не переводятся при смене языка UI.

Измерять: вход и первый лендинг, взаимодействие с демо/методикой, начало и полезное завершение onboarding, триал, первый импорт/принятие знаний, первая/повторная сессия, привычки, серии/достижения, лимиты, выбор тарифа/оплата/продление/отмена, покупка/использование защиты, экспорт/удаление. Различать нажатие «Купить» и подтверждённую оплату; просмотр упражнения и реальную практику; бесплатное демо и активацию. Состав воронок согласован с D01 и разделом 12 ТЗ разработчика.

В свойствах фиксировать допустимые признаки контекста (screen ID, placement, тариф, язык, тип действия, trial eligibility и т.п.), не тексты книг/ответов, личные цели, содержимое привычек или контакты пользователя. Сбор не должен мешать действию, показывать бесконечную загрузку при отказе сервиса или менять интерфейс разных провайдеров. Предусмотреть понятное описание аналитики в политике данных и требуемое управление согласием; запись экрана/сессий не включается автоматически.

Критерий: у каждой ключевой конверсии есть точное определение и событие результата; все системные значения согласованы с разработчиком. Добавление сервиса требует адаптера, но не изменения UX или повторной разметки всех экранов.

### 9.9. Быстрый отклик и стабильность при сетевых сбоях

Бот и Mini App должны немедленно подтверждать действие и устойчиво работать при медленных/потерянных соединениях. Короткая операция не должна выглядеть зависшей из-за фонового импорта, недоступной аналитики или ожидания Telegram. Конкретные транспортные правила и тесты — раздел 3.9 ТЗ разработчика. Истории с потерями соединений на Selectel — исходные кейсы, а не подтверждённая диагностика будущего BrainRecall; фиксированный IP и обещание «всё всегда за 40 мс» в требования не входят.

| Ситуация | Требование к UX |
|---|---|
| Тап по кнопке Mini App | Визуальный pressed/loading и допустимый haptic не позднее 100 мс, без ожидания сети |
| Обычный переход/чтение данных | Сразу локальная оболочка/сохранённое состояние; при ожидании skeleton/status, не пустой экран |
| Inline-кнопка Telegram-бота | Быстро убрать нативное ожидание через callback acknowledgement; затем показать результат. Подтверждение приёма не означает завершение операции |
| Долгая задача, ИИ, импорт | Быстро показать «Принято/В очереди/Обрабатываем» и возможность уйти; реальные этапы, возвращение к той же job |
| Повторный тап/плохая сеть | Одна логическая операция, сохранённый черновик, понятный текущий статус; повтор не покупает второй тариф и не тратит квоту ещё раз |
| Сбой | Локализованное объяснение и безопасное действие «Повторить/Проверить статус»; нет бесконечного spinner, ложного успеха или потери текста |
| Сворачивание/возврат | Восстановить экран и проверить статус, не начинать заново импорт, оплату или ответ |

Проектные целевые показатели при исправной внешней сети и согласованной нагрузке: локальная реакция ≤100 мс; серверный обычный запрос p95 ≤500 мс; результат простой команды бота от получения update сервером до подтверждённого ответа Telegram p95 ≤2 с; приём долгой операции и выдача job/status p95 ≤1 с, без ожидания результата LLM. Это цели приёмки, не гарантия скорости мобильной сети или Telegram. Время долгой задачи измеряется отдельно и не маскируется быстрым ответом «Начали».

При достижении 2 с ожидания результат не считать завершённым: показать статус там, где это технически возможно. После исчерпания бюджета запроса дать конечное состояние или доступный серверный статус задачи. Ошибка отправки служебного «Проверяю…» не должна отменять саму работу и попытку доставить её результат. Нельзя ставить блокирующий экран на всё приложение из-за отказа одного внешнего сервиса. Аналитика/логи не участвуют в ожидании пользовательского действия.

Дизайнер сдаёт loading/queued/reconnecting/failed/unknown-result/retry/success для ключевых flows, включая неясный результат платежа или отправки. Разделять «результат неизвестен, проверяем» и «не выполнено»: не предлагать безусловный повтор опасной операции. Приёмка включает холодный старт, idle/resume, долгую прокрутку, повторные тапы, временную потерю сети и восстановление без дублей.

Три класса маршрутов: (1) локальный CLI/IDE с реально доступными terminal/FS — установка агентом в выданных владельцем пределах; (2) desktop-клиент — поддерживаемый пакет/расширение либо remote connector; (3) облачный web/mobile чат — штатный remote HTTPS connector/OAuth через настройки, если клиент это поддерживает, или честная пошаговая помощь. Установка npm во временном контейнере облачного ассистента не равна подключению MCP к аккаунту пользователя. Название модели само по себе не определяет доступ к конфигам и права.

Единая локализованная точка входа `/install.md?lang=ru|en`, понятный выбор клиента, готовая копируемая инструкция и запасной ручной путь; не подставлять несуществующий пакет или URL. Warm/cold flow и язык owner.locale — по разделу локализации. На экране объяснить, что сделает установка, где локальный/облачный transport, какие данные уйдут провайдеру, какие разрешения нужны. Подключение не означает разрешение на все действия приложения.

Инсталлятор, если выбран: dry-run/проверка среды, конкретный target-клиент, backup и атомарный merge конфигов, без затирания чужих MCP; повторная установка идемпотентна, поддержаны проверка связи, отзыв, удаление и rollback. Другие клиенты не настраивать без выбора владельца. Package version/источник фиксировать для воспроизводимости; публикация и обновление имеют supply-chain проверки. Не встраивать токены в публичные README, query, analytics и историю shell; pairing codes одноразовые с TTL, auth scoped и отзывной. Локальная установка ограничивается sandbox/permissions и может потребовать restart или ручного подтверждения — «100% автоматически» не гарантируется.

В remote MCP — HTTPS, корректный auth по фактически выбранному стандарту/клиенту, проверяемые schemas/annotations и server-side authorization. Подсказки readOnly/destructive/idempotent/openWorld описывают поведение, не заменяют контроль доступа и не гарантируют конкретный UI подтверждения клиента. Нельзя ослаблять auth ради индексатора: публичный discovery только для разрешённых метаданных, приватные данные и операции остаются защищены. Reviewer sandbox изолирован от production и использует отзывной ограниченный доступ, не вечный универсальный обход авторизации.

Если заявлено E2EE — отдельно описать границы доверия локального bridge и cloud connector; локальная установка сама по себе не делает данные невидимыми облачной модели. Не переносить E2EE-обещания AgyLine на этот продукт. Если E2EE нет, явно написать, не добавлять криптографию как маркетинговый ярлык.

Сдать: compatibility matrix, RU/EN install.md и UI подключения/ошибок, реальные инструкции на каждый выбранный клиент, проверку clean install/reinstall/uninstall/revoke/expired code и отрицательных сценариев; для неподтверждённых клиентов честный fallback. Наличие ссылки на исследование не заменяет реализацию/тестирование. Изменения source research не вносят новые функции автоматически: пересмотр матрицы и changelog решения обязателен.

### 11.1. Выбор каналов и границы

До начала заполнить паспорт: аудитория, задача, язык/география, ценность, подтверждённый продуктовый результат, бюджет, ответственный, дата запуска, метрика успеха/порог остановки. Для BrainRecall основной вход — Telegram/лендинг и аудитория обучения, книг и привычек. Технические MCP-каталоги — дополнительный путь только при реально реализованном MCP; продукт не превращается в межагентный мессенджер ради источника. В универсальном применении заменить позиционирование/аудиторию на свой проект.

### 11.3. Реестр задач продвижения и измерение

Для каждой площадки: применимость/N/A с причиной, URL официальных требований, checked_at, ответственный, материалы/версия, статус и дата подачи, замечания, ссылка на опубликованную карточку, следующий шаг. Не подменять этот реестр списком «уже опубликовано» без evidence.

Через общий analytics facade измерять source/campaign → landing → начало onboarding/подключения → первый полезный результат → повторное использование → оплата/удержание; ссылки с безопасной attribution, без токенов и PII. Для MCP добавлять install attempt/success, успешный разрешённый tool call и uninstall/error, не считать скачивания npm реальными людьми. Для Telegram — app open и первый результат, а не одни /start. Если проводится реферальный эксперимент — только добровольное приглашение без чтения адресной книги/рассылки без согласия.

Основные решения — по квалифицированным активациям, времени до результата, удержанию/платной конверсии и затратам поддержки, не по одним звёздам GitHub. Не накручивать stars/downloads, не гонять CI ради популярности, не добавлять нерелевантные topics/aliases и спам-посты. Бейджи и E2EE/security statements только при подтверждённом основании. Проверять правила саморекламы и раскрывать авторство; конкретные рекламные/юридические условия и платные размещения согласовать отдельно.
