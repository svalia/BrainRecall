# BrainRecall — ТЗ для дев-агента

Версия 1.11 · 14 ноября 2026. Разработать Telegram-бот и Mini App по этому документу, `01-designer-brief.md` и согласованным макетам. ID экранов D00–D39 одинаковы в обоих ТЗ. Настоящий документ задаёт поведение и данные; макеты задают представление. При противоречии не угадывать бизнес-правило: зафиксировать расхождение и согласовать его до зависимой реализации.

## 1. Цель, границы и порядок реализации

Пользователь вручную или с помощью ИИ превращает источники в знания и упражнения, регулярно вспоминает их с обратной связью, практикует применение и отслеживает привычки. Целевая платформа — Telegram на iOS/Android, дополнительная — Telegram Desktop/Web. Языки интерфейса — русский и английский, материалы могут быть на других языках.

MVP: Telegram-вход, пять разделов, темы, ручные элементы и упражнения, импорт текста/TXT/MD/текстового PDF/DOCX/EPUB, review кандидатов, адаптивное расписание, сессии, самопроверка и квотируемые ИИ-проверки, привычки, напоминания, статистика, тарифы Stars, триал, экспорт/удаление. Без OCR, аудио, свободного чата с LLM, публичного каталога и доппакетов. Контекст продукта — `../../Knowledge_Habits_Product.md`; его старые цены не применять.

Порядок: (1) shell Telegram и маршрутизация; (2) ручной Free end-to-end; (3) расписание и привычки; (4) импорт и квоты; (5) платежи и жизненный цикл доступа; (6) экспорт/удаление и прогресс; (7) проверка на физических клиентах. Не ждать готового ИИ, чтобы проверить ручной сценарий. Сетевые интеграции заменяемы тестовыми адаптерами. Это ТЗ не означает, что приложение уже построено или опубликовано.

## 2. Рабочая архитектура

Перед стартом проверить фактический репозиторий и инструкции. Если стека нет, рабочее предложение: TypeScript, React/Vite, API на Node.js/Fastify, PostgreSQL, отдельный worker и PostgreSQL-backed очередь. Не поднимать Redis только ради MVP при отсутствии потребности. Выбор библиотеки scheduler закрепить после короткой проверки лицензии и актуальной документации; пользовательские обещания ниже от него не зависят.

Один владелец разрабатывает и поддерживает проект. Selectel сейчас стоит около 3 600 ₽/месяц и обслуживает другие проекты. Не менять чужие сервисы, порты и базы. Выделить свои сервисы/БД/каталог/лимиты CPU и памяти. Общая стоимость сервера не является фактической себестоимостью каждого отдельного пользователя. HTTPS, reverse proxy, отдельные staging и production конфигурации, миграции и проверяемые резервные копии. Production-публикация и расход платного API — отдельные действия в рамках явного поручения владельца; сначала подготовить работающий локальный результат.

Браузер → API → БД; LLM, bot token и платёжная обработка только на сервере. Worker выполняет долгие импорты и напоминания. Секреты через окружение/менеджер секретов, без попадания в клиентский bundle, репозиторий, экспорт или логи. Провайдер ИИ — DeepSeek через заменяемый адаптер. Не переключаться на дорогую модель автоматически.

## 3. Общие требования

### 3.1. Нативная оболочка, верхние отступы и viewport

Использовать официальный Telegram WebApp SDK. Источник API: [Telegram Mini Apps](https://core.telegram.org/bots/webapps). Сведения проверены 10.11.2026. Нативные контролы слева и справа — собственность клиента Telegram; их внешний вид зависит от платформы. Не рисовать их кликабельные копии в DOM.

Нет универсального числа пикселей для верха. Использовать четыре стороны `safeAreaInset` (устройство) и `contentSafeAreaInset` (контролы Telegram), а также обновления `safeAreaChanged` / `contentSafeAreaChanged`. На практике разнести области на вложенные контейнеры: внешний учитывает device safe area, внутренний — Telegram content safe area; контент начинается ещё на 12 px ниже, по бокам получает 16 px. Все fixed/sticky элементы используют ту же систему координат. Не добавлять ещё один набор env(safe-area-inset-*) поверх уже учтённого SDK inset. [Свойства](https://core.telegram.org/bots/webapps#safeareainset), [контентные отступы](https://core.telegram.org/bots/webapps#contentsafeareainset).

Пример контракта layout, а не константы высоты шапки:

```css
.device-safe {
  box-sizing: border-box;
  padding-top: var(--tg-safe-area-inset-top, 0px);
  padding-bottom: var(--tg-safe-area-inset-bottom, 0px);
  padding-left: var(--tg-safe-area-inset-left, 0px);
  padding-right: var(--tg-safe-area-inset-right, 0px);
}
.telegram-content-safe {
  box-sizing: border-box;
  padding-top: var(--tg-content-safe-area-inset-top, 0px);
  padding-bottom: var(--tg-content-safe-area-inset-bottom, 0px);
  padding-left: var(--tg-content-safe-area-inset-left, 0px);
  padding-right: var(--tg-content-safe-area-inset-right, 0px);
}
.screen-content { padding: 12px 16px 16px; }
```

Два слоя должны использоваться однократно. Native header обычного режима уже вне viewport: не добавлять его высоту вручную. Fullscreen — progressive enhancement: успешное открытие не должно от него зависеть. На старом SDK без inset API использовать обычный expanded режим с нативным header, без принудительного fullscreen; вне Telegram preview — собственная оболочка без выдуманных Telegram-кнопок. CSS fallback 0 допустим лишь в этих безопасных режимах, а не как доказательство корректности fullscreen.

Обработать смену темы, fullscreen, viewport, появление клавиатуры и сворачивание. Для устойчивой компоновки использовать стабильную высоту viewport, не пересчитывать всю верстку на каждый промежуточный кадр перетягивания. Для клавиатуры дополнительно проверять видимую область/VisualViewport, прокручивать активное поле и сохранять доступ к CTA. Нижняя навигация занимает место в потоке либо её высота компенсируется в scroll container. Фон может быть под нативными зонами, интерактивное содержимое — нет.

Приёмка: на реальных iOS и Android в обычном и fullscreen режимах первый заголовок, меню и CTA не пересекаются с Назад/Закрыть, вырезом, шевроном и многоточием; после поворота, клавиатуры, сворачивания и смены темы пересечение не появляется. Приложить скриншоты и значения inset для каждого проверенного режима.

#### 3.1.1. Глобальный граббер и нативное сворачивание

Реализовать один общий shell-компонент Grabber/DragHandle на D00–D39, вне scroll container и screen transitions. Визуальный контракт — раздел 9.1.1 дизайнерского ТЗ: 38×5 CSS px, radius 99 px, light #48484A, dark theme token. Не переносить имена `.hsm-*`, чужой version hash и сведения «реализовано» из референса как состояние этого проекта: реализация BrainRecall ещё должна пройти проверку. Имена классов/переменных собственные, например `.app-grabber`, `--app-grabber-y`.

В fullscreen, когда Telegram-контролы находятся над областью WebView, исходная позиция центра: `y = safeAreaInset.top + contentSafeAreaInset.top / 2`, `left: 50%`, `transform: translate(-50%, -50%)` относительно viewport-origin, не уже inset-контейнера (иначе top учтётся дважды). При каждом обновлении inset/fullscreen/viewport/theme пересчитать. Граббер и theme gradient — отдельный декоративный слой с `pointer-events: none`, `aria-hidden: true`, без tab stop. Верхний слой не меняет уже рассчитанные безопасные отступы контента. Clamp/visibility guard исключает вырез/status bar/нулевой content inset; окончательное выравнивание подтвердить на реальных iOS/Android, поскольку API не отдаёт bounding boxes нативных кнопок.

Нативный header обычного режима вне DOM: приложение не может вставить в него HTML или достоверно измерить его кнопки. Здесь использовать штатный handle клиента, если доступен; иначе fallback верхней доступной границы без фальшивого header и без повторной полоски. Внешний browser preview/Desktop не показывают обещание мобильного жеста, если он не поддерживается. Не форсировать fullscreen только ради декора при отказе API.

**Жест:** сохранять нативное поведение Telegram; на поддерживаемых клиентах включить `enableVerticalSwipes()` (API 7.7+) и не оставлять глобальный запрет свайпов при смене экранов. Не ставить `preventDefault`, pointer capture, непрозрачный touch overlay или глобальный `touch-action: none` на область граббера/нативного header. При конфликте внутреннего bottom sheet ограничить обработчик его областью и вернуть исходное состояние SDK после закрытия. При scroll страницы граббер неподвижен, нативный header остаётся доступен для свайпа; нельзя обещать, что любой свайп по содержимому независимо от scroll position сворачивает любой клиент.

**Уточнение API:** на дату проверки 10.11.2026 в публичном [Telegram WebApp API](https://core.telegram.org/bots/webapps#initializing-mini-apps) отсутствует документированный `Telegram.WebApp.minimize()`. Не вызывать его как гарантированно существующий и не использовать `close()`/`exitFullscreen()`/browser history как эквивалент сворачивания. Текущий обязательный путь — нативный жест. Дополнительный custom swipe из центральной верхней зоны возможен только если при реализации найден официальный документированный метод сворачивания в целевых клиентах: обновить ссылку/минимальную версию, feature detection и тесты; иначе не включать фиктивный JS-обработчик. Отсутствие такого метода не блокирует нативное сворачивание.

Сохранять завершённые действия на сервере и черновики по существующим правилам; на deactivated не считать сессию завершённой/пропущенной и не сбрасывать маршрут. При activated сверить актуальные данные и восстановить scroll/answer draft, не запускать автоматически импорт/покупку. Нельзя гарантировать сохранение JS-памяти после выгрузки WebView ОС, поэтому восстановление не должно зависеть только от неё.

Приёмка на реальных клиентах: (1) fullscreen + обычный режим, (2) обе темы, (3) длинный scroll не сдвигает полоску, (4) переходы всех типов экранов, (5) keyboard, вырез и изменение inset, (6) свайп доступной верхней зоны при scrollTop=0 и scrollTop>0, (7) внутренний sheet не сворачивает приложение неожиданно, (8) возврат без потери текущего задания, (9) unsupported/Desktop fallback без вызова отсутствующего API, (10) invoice и нативные кнопки не перекрыты. Зафиксировать клиент/версию и фактический результат; скриншот чужого свернутого приложения не является доказательством реализации BrainRecall.

### 3.2. Тактильный отклик

Единый адаптер над официальным `Telegram.WebApp.HapticFeedback` с проверкой поддержки (API 6.1+) и пользовательской настройкой. [API](https://core.telegram.org/bots/webapps#hapticfeedback).

| Событие продукта | Вызов |
|---|---|
| Активная кнопка/переход по тапу | `impactOccurred('light')` |
| Реальное изменение переключателя/выбора | `selectionChanged()` |
| Сохранено, привычка отмечена, сессия завершена | `notificationOccurred('success')` |
| Действие требует внимания | `notificationOccurred('warning')` |
| Ошибка выполненной операции | `notificationOccurred('error')` |

Один результат не дублировать impact+notification. Не вызывать на скролл, ввод букв, неизменившийся выбор, disabled или фоновые ошибки. Неверный учебный ответ не наказывать сильной вибрацией: мягкая обратная связь/без haptic. Поддержка зависит от устройства, отказ адаптера не ломает действие; не использовать navigator.vibrate как замену официальному API. При выключенной настройке вызовов нет.

### 3.3. Иерархический нативный Назад

`BackButton.onClick` направлять в собственный navigation controller, не в `window.history.back()`. Единственная подписка с cleanup. Каждый route содержит `screenId`, параметры, `parent`, допустимый временный overlay и состояние черновика. На пяти корневых вкладках BackButton скрыт; переключение вкладок не создаёт цепочку возврата. [API кнопки](https://core.telegram.org/bots/webapps#backbutton).

Приоритет: закрыть overlay → обработать dirty guard/паузу → перейти к родителю. Deep link не меняет родителя: знание → его тема → Знания; привычка → Привычки. Вложенный временный просмотр источника возвращает в инициатор с тем же answer draft. Для обычных форм сохранение возвращает к владельцу объекта; мастер хранит шаги отдельно. URL допустимо синхронизировать с маршрутом, но browser history не определяет продуктовую иерархию. Аппаратный/браузерный back внутри приложения приводить к тому же контроллеру насколько клиент позволяет; не перехватывать системное закрытие ОС.

Закрытие Telegram не тождественно Назад. Черновики сохранять, при риске потери включать нативное подтверждение закрытия с feature detection. Нельзя гарантировать блокировку любого принудительного завершения приложения: серверное сохранение завершённых действий обязательно.

### 3.4. Только портрет на поддерживаемых мобильных клиентах

Выбор владельца: портретная ориентация. API 8.0+ `lockOrientation()` блокирует текущий режим без аргумента. На мобильном при портретном положении вызвать метод; при старте горизонтально предложить повернуть телефон, дождаться реального портретного положения и только затем заблокировать. Не определять ориентацию только по отношению ширины/высоты после открытия клавиатуры; использовать доступные screen orientation и состояние перед клавиатурой с проверкой на клиентах. [Метод](https://core.telegram.org/bots/webapps#initializing-mini-apps).

При неподдерживаемом API либо невозможности получить портрет — рабочий responsive fallback, без CSS rotate всего приложения. На Desktop/Web — центрированная колонка, не заглушка с требованием повернуть монитор. Если клиент не умеет фиксировать режим, не обещать жёсткую блокировку. Тест: открытие вертикально, поворот после блокировки, старт горизонтально, клавиатура и возвращение из background.

### 3.5. Доступность и устойчивость

Контраст 4,5:1 для обычного текста, цели от 44×44 CSS px, keyboard/focus/labels, масштаб текста 200%, reduced motion, две темы Telegram. Нет горизонтального скролла всей страницы; формулы допускают локальный scroll. Никаких действий только по цвету/haptic/hover. Локальный tap feedback не ждёт сети; загрузка блокирует только повтор той же операции. Асинхронные статусы честные, без фиктивного процента.

### 3.6. Локализация (i18n): Telegram Bot + Mini App + Web / API / MCP

Актуальная редакция требований владельца от 14.11.2026. Полностью заменяет прежний текст этого раздела, включая старые дополнения о гибридной локализации и правила Homestead Prime. Первый релиз BrainRecall включает полные ru/en. Ниже приведён новый единый контракт; отдельной альтернативной схемы profile.language/ui_locale больше нет.

#### 1. Единый источник правды (Single Source of Truth)
- Все переводы хранятся в структурированных JSON-каталогах на бэкенде: `locales/<lang>.json` (например, `ru.json`, `en.json`).
- Структура ключей единая и иерархическая для всех слоёв продукта:
  - `meta.*` — код языка (`code`), название языка (`label`), направление текста (`dir`).
  - `bot.*` — все сообщения, кнопки (`InlineKeyboard` / `ReplyKeyboard`), команды, алерты и ошибки Telegram-бота.
  - `miniapp.*` — все экраны, вкладки, модалки/шторки, плейсхолдеры, aria-атрибуты, тосты и ошибки валидации Mini App.
  - `api.*` / `mcp.*` — пользовательские тексты ошибок API, описания инструментов/ресурсов и системные инструкции для внешних клиентов.
- Строгий паритет ключей: набор ключей во всех `locales/*.json` должен на 100% совпадать.
- Подстановка переменных в строках выполняется через именованные плейсхолдеры `{var_name}` (одинаковый формат на бэкенде и фронтенде).

#### 2. Приоритет определения языка и флаг ручного выбора (`locale_override`)
У каждого пользователя в БД хранятся два поля:
- `locale: str` (нормализованный код языка, например `"ru"` или `"en"`, с дефолтным fallback).
- `locale_override: bool` (по умолчанию `False` — менял ли пользователь язык вручную в настройках).

Правила синхронизации языка:
1. **Первый вход (в бота или Mini App):**
   - Берётся `language_code` из объекта `from` апдейта Telegram или `initDataUnsafe.user.language_code` в WebApp.
   - Нормализуется по базовому IETF-тегу (`"en-US"` -> `"en"`, `"ru-RU"` -> `"ru"`; неподдерживаемые языки -> дефолтный язык).
   - Сохраняется в `user.locale` при `locale_override = False`.
2. **Повторные запросы от Telegram:**
   - Если `user.locale_override == False`, `user.locale` автоматически обновляется при смене языка клиента Telegram.
   - Если `user.locale_override == True`, язык из клиента Telegram **не перезаписывает** выбор пользователя.
3. **Ручное переключение языка в настройках Mini App (или командой `/lang` в боте):**
   - Отправляет `PATCH /api/v1/settings` с `{ "locale": "<lang>" }`.
   - Бэкенд выставляет `user.locale = <lang>` и `user.locale_override = True`.
   - Выбор сразу применяется и в Mini App, и во всех последующих сообщениях бота, и во внешних интеграциях (API / MCP).

#### 3. Архитектура локализации в Telegram Mini App
- **Эндпоинт каталога:** `GET /api/v1/i18n?lang=<lang>` возвращает слитый с базовым языком каталог (чтобы при отсутствии ключа в переводе автоматически подставлялся дефолтный язык, а не сырой ключ).
- **Порядок инициализации (`bootstrap`):**
  1. До первого рендера UI определяется стартовый язык: `localStorage/CloudStorage ("locale")` -> `Telegram.WebApp.initDataUnsafe.user.language_code` -> дефолтный язык.
  2. Загружается каталог `/api/v1/i18n?lang=<initialLang>` (или берётся из кэша), разворачивается словарь строк и только после этого вызывается первый `render()`.
  3. После ответа `GET /api/v1/me` сверяется `me.user.locale`: если на сервере сохранён другой язык, догружается нужный каталог и UI перерисовывается.
- **Мгновенное переключение без перезагрузки:**
  - Переключатель языка (`RU / EN`) в настройках обновляет `state.locale`, кэширует выбор в `localStorage` / `Telegram.WebApp.CloudStorage`, подгружает словарь, синхронно вызывает `render()`, меняет `<html lang="...">` и отправляет `PATCH /api/v1/settings`.
- **Защита от типичных багов во фронтенде:**
  - Функция перевода `t(key, vars)` должна иметь зарезервированное имя: внутри рендер-функций и обработчиков событий **запрещено** называть локальные переменные `const t = ...` или параметры `(t) => ...`, чтобы не перекрывать `t()`.
  - Даты, время и числительные форматируются с учётом `state.locale` (`Intl.DateTimeFormat(state.locale === "en" ? "en-US" : "ru-RU", ...)`).

#### 4. Локализация Telegram-бота
- Все обработчики команд (`/start`, `/help`, `/settings` и др.), callback-кнопок и фоновых уведомлений получают `user.locale` и формируют тексты/кнопки только через `t("bot.*", user.locale, **vars)`.
- При смене языка в Mini App новые уведомления и карточки от бота сразу приходят на выбранном языке.
- Меню команд бота (`setMyCommands`) регистрируется отдельно для каждого поддерживаемого `language_code` (`ru`, `en`, и дефолтный без `language_code`).

#### 5. Гибридный флоу для лендинга, документации и внешних клиентов (MCP / CLI / Web)
Должны поддерживаться оба сценария входа пользователя:

##### Сценарий А — Пользователь сначала зашёл в бота или Mini App (Warm Start)
- Язык пользователя уже известен (`user.locale`).
- Генерируемые в боте и Mini App команды установки, промпты для ИИ-агентов и инструкции отдаются на языке `user.locale` (с явным параметром `?lang=<locale>` в ссылках на инструкции, например `https://.../install.md?lang=en`).
- Когда внешний клиент / MCP-сервер подключается по токену или коду привязки этого пользователя, сервер читает `owner.locale` и автоматически отдаёт описания инструментов (`tools/list`), ресурсы (`resources/list`), системные инструкции (`initialize`) и ответы/ошибки на языке владельца.

##### Сценарий Б — Холодный старт с лендинга, GitHub или маркетплейса до входа в бота (Cold Start)
- Публичные веб-страницы (`/`, `/guide`, `/install.md`, `/oauth/authorize`) определяют язык по приоритету:
  1. Явный query-параметр `?lang=en|ru` в URL;
  2. Сохранённый выбор `localStorage` в браузере + видимый переключатель `RU | EN` в шапке сайта;
  3. Заголовок `Accept-Language` браузера/клиента;
  4. Дефолтный язык (на международных площадках GitHub / npm / MCP-маркетплейсах базовые README и команды публикуются на английском или содержат `?lang=en`).
- Команда, скопированная с английской версии лендинга или из README на GitHub/npm, содержит `?lang=en`, поэтому агент сразу получает английский `install.md` и ведёт онбординг на английском ещё до привязки аккаунта Telegram.

#### 6. Автоматическая проверка перед деплоем (Checklist)
1. Скрипт проверки паритета ключей: все ключи из `ru.json` присутствуют в `en.json` и наоборот.
2. Скрипт проверки покрытия в коде: каждый вызов `t("...")` в коде бота и Mini App ссылается на существующий ключ в JSON-каталогах.
3. Проверка отсутствия захардкоженной кириллицы в UI-шаблонах и отсутствии перекрытия (`shadowing`) функции `t`.

#### Применение к BrainRecall и уточнения реализации

- Минимум две полные локали ru/en с первого релиза. DEFAULT_LOCALE задаётся централизованным конфигом (для основного приложения базовый ru); публичные GitHub/npm/MCP-материалы имеют английский базовый текст. Неподдерживаемый код нормализуется в поддерживаемый default, а не создаёт новую локаль произвольно. Дальнейшие локали добавляются валидным файлом и декларативными meta, без переписывания бизнес-логики.
- В профиле хранятся только canonical `locale` и `locale_override`; ответ `GET /api/v1/me` содержит `me.user.locale` и `me.user.locale_override`. Поля profile.language/ui_locale из прежней редакции не являются вторым источником. При миграции перенести старый явный выбор в locale_override=true, не обнулить preference существующего пользователя. Свойство аналитики языка также `locale`.
- Telegram language_code опционален. Сервер обновляет locale при override=false только из достоверного Telegram update/проверенного initData. Отсутствующее поле не сбрасывает уже сохранённый язык; при первом входе без поля используется default. initDataUnsafe годится лишь как предварительная клиентская подсказка, не для авторизации. На активном веб-сеансе Telegram может не прислать изменение языка мгновенно: синхронизация выполняется при следующем достоверном входе/update, не обещать несуществующее push-событие.
- D26 получает рабочий RU/EN-переключатель, /lang в боте — выбор того же свойства через общий settings service. Политика ручного выбора одинакова у бота и Mini App. Старый POST /api/profile заменён PATCH /api/v1/settings; публичный i18n использует query `lang`, не старый `locale`. Если понадобится совместимость старых клиентов, это временный явный alias с датой удаления, не два конкурирующих контракта.
- Переключение сначала загружает валидный каталог, затем атомарно обновляет state/cache/html lang (и dir из meta); во время загрузки остаётся читаемый текущий UI. Сохранение на сервере показывает saving/error/retry без ложного success; при неуспехе optimistic выбор явно pending или откатывается. CloudStorage асинхронен: не блокировать первый рендер бесконечно и не позволять позднему старому ответу перезаписать новый выбор. После me серверный выбор корректирует предварительный cache. Смена языка не теряет форму, сессию, timezone и не запускает LLM.
- Иерархия ключей строго meta/bot/miniapp/api/mcp, включая лендинг в miniapp либо отдельный согласованный раздел с паритетом во всех каталогах. Не сохранять старые независимые namespaces как второй набор переводов. В каждом meta различаются значения code/label/dir, но структура ключей совпадает. Именованные {var_name} и plural-контракт едины; проверяется также паритет имён параметров и типов, экранирование и безопасный rich text. t — зарезервировано для translator, lint запрещает shadowing.
- Строгий паритет и merged fallback не противоречат: CI не выпускает неполный пакет, runtime merge с базовой локалью защищает от повреждённого cache/несовместимой версии. t не показывает сырой ключ пользователю; отсутствующий в базовом каталоге ключ — ошибка разработки. Веб получает лишь разрешённую публичную проекцию каталога; секреты и приватные LLM system prompts не выдаются через /api/v1/i18n. Версия каталога, cache/ETag и защита от path traversal обязательны.
- Нативные имя/описания профиля и setMyCommands по языкам/default остаются отдельной витриной Telegram; локализуются описания команд, не сами /start и /lang. Подготовить RU/EN preview-медиа BotFather. Telegram выбирает эту витрину по своему языку: ручной locale нашего приложения сам по себе не меняет весь язык клиента Telegram.
- Для авторизованного внешнего API/MCP язык берётся из owner.locale; до авторизации публичный Web использует query → browser choice → Accept-Language → default. HTTP-сервер не может читать localStorage напрямую: браузер передаёт выбранную locale явным параметром/разрешённым механизмом; markdown/CLI-клиенты без browser storage используют query/Accept-Language/default. Недоверенный lang валидируется, не изменяет чужой профиль и не попадает в shell без безопасного формирования команд.
- MCP/CLI/GitHub/npm-пункты обязательны для соответствующих реально существующих/публикуемых компонентов, но не добавляют разработку нового MCP-сервера в MVP автоматически. При наличии MCP tools/list, resources/list и initialize instructions локализуются по owner.locale — прежнее правило «описания инструментов всегда English» отменено. Идентификаторы tools/параметров и JSON schemas остаются стабильными; при смене locale обновлять объявления/кеш в рамках возможностей MCP-клиента, при необходимости уведомлять о refresh/reconnect. Не обещать обновление уже кешированного списка в любом клиенте без его поддержки. Ответы и ошибки всегда на актуальном языке владельца.
- В макетах D00–D39 проверить реальные RU/EN строки, 200% шрифт и расширение перевода на 30–50%; переносы/размеры не должны ломать safe areas и CTA. В пользовательском контенте допустим исходный язык. Псевдолокаль — дополнительная QA-проверка, не замена настоящего en.
- Сдача: парные ru/en каталоги, аннотации ключей для дизайна, lint/parity/coverage отчёты, отсутствие hardcoded системной кириллицы (пользовательский контент/тестовые fixtures исключать обоснованно), проверки locale_override=false/true при смене Telegram language, bootstrap/cache/me, тостов/модалок/бота/дат, warm/cold внешнего входа. Реализованные экраны/сервисы должны ссылаться на этот единый контракт.

### 3.7. Обязательное удаление пользователя из профиля

Наличие сохранённого аккаунта — даже созданного автоматически по Telegram ID без формы регистрации — требует пункта **«Удалить аккаунт и данные» в D26** с переходом к подтверждению D32. Никакой оплаты, активной подписки, обращения в поддержку или обязательного экспорта для этого не нужно. Удаляется аккаунт приложения, не Telegram пользователя.

После подтверждения сервер создаёт идемпотентную DeletionJob и запрещает новые учебные/ИИ/платёжные операции аккаунта, отзывает все его сессии, прекращает обычные уведомления, отменяет pending jobs и автопродление по правилам платежей. Если отмена Telegram временно недоступна, задача продолжает retries и показывает честный статус; нельзя сообщить «всё удалено», скрыв продолжающееся продление. Короткоживущий deletion-status token допустим только для чтения статуса удаления, не доступа к старому аккаунту.

Удалить связи и содержимое: профиль/Telegram-связку, preferences/consents по применимой политике, темы, исходники и object-storage файлы, fragments, candidates/import jobs, знания/упражнения, ответы/attempts/reviews, планы/сессии, привычки/occurrences, reminders, серии/grants/celebrations, freeze stock/intervals, exports и ссылки скачивания, cache/search indexes, идентифицирующую продуктовую аналитику и прочие зависимые записи. Не ограничиваться soft-delete строки User с сохранёнными читаемыми файлами. Изолировать исключения для минимального обязательного платёжного/аудиторского хранения, документировать правовое основание и сроки; они не дают восстановить учебный профиль.

Очистка рабочих данных — срок из раздела 13, backups — до ротации по той же политике; при restore применять журнал удаления до открытия пользовательского доступа. Не держать исходный Telegram ID/полный контент в бессрочной tombstone: минимальная запись для suppression восстановления с ограниченным доступом/сроком и подходящим основанием. Не обещать немедленное стирание у внешнего LLM-провайдера без подтверждённой возможности; до передачи раскрыть его политику. При повторном входе — новый пустой аккаунт, старые данные не присоединяются, история платежей сама не восстанавливает старый профиль. Правило одноразового trial согласовать с минимальной разрешённой anti-abuse записью, не хранить удалённое учебное содержимое ради проверки trial.

Удаление выполняется асинхронно с retries/audit и контролем orphan files, не одной длинной HTTP-транзакцией. До завершения статус pending, после очистки — completed с объяснением оставшихся законных исключений. Проверить ownership, CSRF/session защиту и явное подтверждение; операция одного пользователя не касается остальных проектов на общем сервере.

Приёмка: аккаунт Telegram-входа без ручной регистрации можно удалить из профиля; старые сессии/URL файлов/экспортов больше не работают; worker не воссоздаёт данные после удаления; подписка не продолжает скрыто списываться; fresh login пустой; restore backup не возвращает удалённое; оставшийся платёжный аудит изолирован и объяснён. Подробная эксплуатация — раздел 13.

### 3.8. Независимый слой аналитики и подключаемые адаптеры

Внедрение аналитики обязательно для первого релиза; окончательный внешний сервис выбирается позже. Сейчас реализовать контракт, инструментирование Mini App/бота/API, внутренний collector/storage adapter и тестовый/no-op adapter. Не подключать пять SDK и не оплачивать сервисы заранее. No-op нужен для тестов/отключения, но не заменяет работающий сбор в production. После выбора поставщика добавить и проверить его адаптер без изменений бизнес-модулей и мест отправки событий.

**Архитектура:** продуктовый код → единый facade → проверка схем/identity/privacy → collector + очередь доставки → разрешённые destination adapters. При необходимости внешний browser SDK подключается только внутри адаптера и после соответствующей проверки consent. Список провайдеров задаётся конфигурацией; возможен fan-out нескольких разрешённых направлений. Код UI/бота/платежей не вызывает напрямую amplitude/gtag/ym/posthog. SDK keys, endpoints, region и включение провайдера — config, закрытые API keys только на сервере.

Интерфейс facade:

```ts
track(eventName, eventProperties, context?)
identify(analyticsUserId)
setUserProperties(properties)
setUserPropertiesOnce(properties)
unsetUserProperties(propertyNames)
resetIdentity()
setCollectionAllowed(allowed)
flush()
```

Это семантический контракт, не обещание идентичных нативных функций всех систем. Для erase нужен отдельный серверный `deleteAnalyticsUser(userId)` с delivery/status, а не путаница с resetIdentity (он только очищает локальную идентификацию). Сервис может не поддерживать set-once/unset/merge/delete напрямую: адаптер описывает capability matrix и преобразование/ограничение; emulation только на нашем collector, если сохраняет смысл. Не терять неподдерживаемые данные молча и не обещать переносимость dashboards/session replay/атрибуции один к одному.

**Каноническая модель:** event_id UUID, event_name, schema_version, occurred_at UTC, received_at, source client/bot/server, environment, app_version, anonymous_id (если разрешён), analytics_user_id, session_id, event_properties, допустимый snapshot user properties. Пользовательские свойства отдельны: set/set_once/unset с timestamp/version. Обязательные event names и enum — стабильные snake_case, не строки русского UI. Каталог tracking plan хранится в репозитории: описание, момент, владелец, источник истины, свойства/типы/обязательность, PII classification и version. Валидация на клиенте и collector, ограничения размера/кардинальности/вложенности; запрещённые поля отбрасывать с диагностикой без записи их содержимого.

**Идентификация:** собственный непрозрачный analytics_user_id, не Telegram ID/username/телефон. Соединять с авторизованным профилем только после серверной проверки; клиент не может отправлять события за чужого пользователя. До входа допустим ограниченный anonymous ID при разрешённом сборе. После входа связать историю только поддерживаемым/проверенным способом адаптера, без склейки разных людей на общем устройстве. Logout/удаление сбрасывает локальную identity и запрещает доставку старых событий под новым аккаунтом. Смена устройства даёт тот же идентифицированный user ID; session_id и anonymous_id не подменяют личность. Не передавать initData, токены, URL с чувствительными параметрами, содержимое книг, свободных ответов и личных привычек.

User properties: locale, timezone (если нужен и разрешён), plan_code, subscription_status, trial_status, signup_at, acquisition_source, app/platform version, разрешённые experiment assignments. Event properties: screen_id, placement, item/exercise type, grading_mode, assisted, elapsed bucket, operation type, plan/price/prompt/scheduler version, result/error_code, quantity и currency XTR для оплаты. Конкретные identity и перечень полей — allowlist. Важные сегменты тарифа/языка на момент события сохранять как snapshot, чтобы будущая смена тарифа не переписывала прошлый контекст.

**Достоверность:** успех оплаты/продления/refund, квоты, trial start, grant/consume защиты и достижения отправляет сервер из подтверждённой транзакции через transactional outbox. UI отправляет intent/view/click, не подтверждённую выручку. Не дублировать одно событие клиентом и сервером: один owner/source на canonical fact. event_id сохраняется при retries, дедуп на collector и доступных destination механизмах; at-least-once с контролем дублей, не обещание exactly-once у всех провайдеров. Аналитическая очередь и её ошибка не откатывают пользовательскую оплату/занятие; outbox восстанавливает доставку. Таймауты, retry/backoff, TTL/размер очередей, dead letter и метрики ошибок/лагов обязательны; не бесконечно копить данные при выключенном провайдере.

**Подключаемые сервисы:**

| Назначение | Что должен учитывать будущий адаптер |
|---|---|
| Amplitude | События отдельно от свойств пользователя/identify; собственный mapping identity и типов. [Документация](https://amplitude.com/docs/data/user-properties-and-events) |
| Self-host PostHog | Capture/identity/person properties через адаптер; host и версия развёртывания задаются позднее. Совместимость реально выбранной self-host версии проверить до подключения, не считать её гарантированно равной cloud |
| Google Analytics 4 | Сопоставление custom/recommended events, parameters, user properties и нужных custom definitions; provider-specific ограничения/identity/session semantics. [События GA4](https://developers.google.com/analytics/devguides/collection/ga4/reference/events) |
| Яндекс Метрика | Маппинг просмотров/целей/параметров визита и пользователя, user ID; проверить доступность выбранного server-side/browser пути, не считать произвольный track нативно тем же reachGoal. [User parameters](https://yandex.com/support/metrica/en/objects/user-params) |
| Metabase | Не прямой event SDK: сохранять canonical events/user traits в своей аналитической схеме/БД, предоставить read-only представления/витрины и подключить Metabase. [Подключение БД](https://www.metabase.com/docs/latest/databases/connecting) |

Внутреннее хранилище MVP может быть отдельной schema PostgreSQL с events, identity mapping и user-property history/витринами; не ставить тяжёлый warehouse только ради обёртки. Для Metabase отдельная read-only роль, без доступа к секретам/сырому пользовательскому контенту и без опасных аналитических запросов к production-транзакциям. Рост объёма — лимиты/партиции/срок хранения, дальнейший вынос по измерениям.

**Приватность/удаление:** определить разрешённый режим сбора и необходимые согласия до внешней отправки; collector и adapters исполняют политику одинаково. Session replay/autocapture записей ввода выключены по умолчанию и не входят автоматически в эту интеграцию. Account deletion очищает идентифицируемую аналитику/identity mapping/очереди и запускает удаление у фактически подключённых провайдеров; поздний retry не должен воссоздать профиль. Отозванное разрешение останавливает дальнейший необязательный сбор/доставку, очереди обрабатываются по политике без обхода через сервер. Не включать скрытый полный payload в диагностические логи.

**Приёмка:** tracking plan всех ключевых сценариев реализован и просматривается в локальном debug sink; fake adapter получает одинаковые canonical факты из web/bot/server; пропуск оплаты/двойной webhook не дублирует revenue; identify/reset не склеивает пользователей; ретраи сохраняют event_id; новые свойства не ломают старую схему; отключённая/недоступная аналитика не ломает приложение; удаление/отзыв согласия предотвращают повторную доставку. Добавление нового destination затрагивает адаптер/config/его контрактные тесты, не места track во всём приложении. Реальная проверка выбранного провайдера отдельна: до выбора не заявлять, что интеграция с ним уже реализована.

### 3.9. Стабильный транспорт, немедленный отклик и диагностика задержек

Обязательный общий контракт для Telegram-бота, Mini App API и внешних интеграций. Исходные кейсы владельца указывают на опасный антипаттерн: новый HTTP-клиент на каждый вызов плюс долгий connect timeout и последовательное ожидание служебных запросов. Их описанная причина с SYN-потерями не считается независимо проверенным фактом BrainRecall: собственную диагностику провести до инфраструктурных изменений. Выбор фреймворка сам по себе стабильность не гарантирует.

**1. Клиенты живут весь lifecycle приложения.** Создавать управляемый HTTP client/session и connection pool при старте процесса, переиспользовать TCP/TLS Keep-Alive, закрывать при graceful shutdown. Запрещён `new client`/`async with AsyncClient` внутри каждого Telegram вызова, одноразовые requests.post в рабочем цикле и отключённый reuse без причины. В Python это requests.Session/httpx.AsyncClient/aiohttp.ClientSession; в рабочем Node-стеке — общий HTTP dispatcher/agent с pooling. Примеры не означают смену стека. [HTTPX: clients и reuse](https://www.python-httpx.org/advanced/clients/).

Не обещать один вечный сокет: Telegram/LB/NAT закрывают idle соединения, pool должен переподключаться и удалять повреждённые подключения. Настроить bounded max connections/keep-alive connections/idle expiry и проверить на версии выбранной библиотеки. Полностью читать/закрывать response body, не терять слоты. Long polling, обычные Telegram RPC, LLM и file uploads изолировать отдельными пулами/резервами concurrency по их ролям. Один долгий getUpdates не должен занимать единственный слот для answerCallbackQuery/sendMessage. Не делить небезопасную синхронную Session между потоками без политики владения.

**2. Раздельные таймауты и общий deadline.** Все внешние вызовы имеют connect/read/write/pool timeout и wall-clock budget, включающий попытки и задержки. Read timeout конкретной библиотеки может означать ожидание следующего chunk, а не полный срок запроса — total deadline задаётся отдельно. [HTTPX: типы таймаутов](https://www.python-httpx.org/advanced/timeouts/).

Начальные инженерные настройки, уточняемые замерами, не требования провайдера:

| Операция | Connect / ожидание pool | Read / общий бюджет |
|---|---|---|
| Короткий Telegram RPC | connect 3 с, pool 0,5 с | read 5 с, write 5 с; foreground total ≤8 с, retries внутри него |
| Callback acknowledgement | тот же pool с высоким приоритетом | общий бюджет ≤2 с; не ожидать все обычные retries перед работой handler |
| getUpdates long poll | connect 3 с, отдельный pool | server timeout 25 с, read 35 с, total одной попытки 40 с; ожидание пустого poll не ошибка |
| Обычный Mini App API | ограниченное ожидание БД/зависимостей | foreground deadline ≤8 с; долгую работу вернуть job ID, не держать HTTP до конца |
| LLM / парсинг / upload | отдельный транспорт/worker | собственные лимиты времени/размера и cancellation из job policy, не короткий Telegram timeout |

Таймаут 30–60 с на установление нового TCP для простой команды недопустим. Долгий read для long polling допустим и не увеличивает connect timeout. Timeout/error одного запроса не закрывает общий клиент целиком и не валит процесс. Ограничить также запросы БД и ожидание lock: pooling Telegram не исправляет зависание SQL.

**3. Повторы по смыслу операции, не вслепую.** Retry только классифицированных временных ошибок, с ограничением попыток/total deadline, exponential backoff+jitter; пример для connect failure: максимум 3 попытки, задержки 0,25/0,75 с с jitter, если позволяет общий бюджет. Нельзя умножать retries SDK × wrapper × очередь без единого лимита. Telegram 429 обрабатывается по retry_after; если ждать дольше foreground budget — перенести в очередь/показать статус, не засыпать в event loop. 400 invalid input/старый callback, 401, 403 blocked не повторять бесконечно; 409 polling conflict — проблема конфигурации/лидера, не повод запускать ещё один poller.

У ConnectTimeout до отправки тела обычно есть безопасная возможность повторить. После записи запроса ReadTimeout/обрыв может означать «Telegram выполнил, ответ потерян». Для sendMessage нет универсального идемпотентного ключа Telegram: нельзя обещать exactly-once или механически повторять все отправки. Использовать локальный outbox с unique intent/update ID, сохранять delivery state sent/failed/unknown и message_id при наличии; проверять/минимизировать повторы, предпочитать edit известного сообщения. Для unknown явно принять политику допустимых дублей уведомлений, не терять результат молча. Внутренние платежи/квоты/защиты/attempts остаются идемпотентными независимо от сетевых повторов.

**4. Callback acknowledgement отделён от работы.** На inline callback быстро вызвать answerCallbackQuery без ожидания SQL-отчёта/LLM/парсинга. Задача handler стартует независимо от сбоя acknowledgement: catch/log ограниченного ack, не прерывать полезный ответ цепочкой `await ack; await send`, если ack упал. Локальная ошибка отправки «Проверяю…» также не отменяет job и финальный результат. Быстрый ack не является подтверждением покупки, сохранения или успешного выполнения. [Telegram API](https://core.telegram.org/bots/api#answercallbackquery).

Обработчики асинхронны: никакого requests/time.sleep/CPU-парсинга в event loop. Blocking I/O/CPU — bounded worker/thread/process с таймаутом; не неограниченный spawn. Один медленный пользователь/провайдер не задерживает остальных. Интерактивные ответы/ack/pre-checkout имеют приоритет над массовыми reminders/аналитикой, с учётом Telegram rate limits.

**5. Надёжный приём updates.** Выбрать webhook либо long polling, не оба одновременно для одного token. Webhook: проверить secret и минимальную схему, надёжно сохранить update/dedup ID в очереди/БД, быстро вернуть успешный HTTP; долгую работу делать worker. Если persist не удался — не отдавать ложный success, чтобы Telegram мог повторить. Long poll: один активный poller на token, durable update_id/offset, подтверждать offset после надёжного сохранения для обработки, а не перед этим; фактические handler могут завершаться позже. Повтор доставки не повторяет бизнес-мутацию. При restart не удалять pending updates по умолчанию. [getUpdates](https://core.telegram.org/bots/api#getupdates).

**6. Фоновые задачи и изоляция сбоев.** Импорт/LLM/внешний сайт работают как jobs с подтверждённым приёмом, checkpoints, статусом и возможностью возобновления после рестарта. Telegram delivery результата — отдельный outbox, сбой отправки не удаляет сам результат. Ограничить очереди/concurrency, backpressure, retries и dead-letter. Временный отказ аналитики/LLM не делает health/readiness всего ручного Free красным без причины; различать критическую недоступность БД и degraded внешнего канала. Circuit breaker при длительном отказе провайдера с half-open пробой допустим, но не должен навечно блокировать канал после восстановления.

**7. DNS/TLS/маршрут — через диагностику, не фиксированный адрес.** api.telegram.org использовать как hostname с проверкой сертификата/SNI; не отключать verify TLS. Не хардкодить 149.154.167.220, другой единичный IP или запись /etc/hosts как универсальное production-решение. Если DNS/маршрут плохи: отдельно измерить DNS, TCP connect, TLS, TTFB, cold/warm, IPv4/IPv6 и состояние pool; сопоставить с логами/сетевой трассировкой без секретов. SYN loss не выводить только из ConnectTimeout или отсутствия ESTAB: это разные возможные причины. Hosts/proxy/egress workaround возможен лишь как отдельное документированное инфраструктурное решение с TLS, сроком, мониторингом и rollback. Не менять общий сервер/соседние проекты автоматически.

**8. Наблюдаемость и бюджет задержки.** Correlation: update_id/callback_id/request_id/job_id/outbox_id, метод, attempt, error class, latency, queue delay, повторное/новое соединение там, где поддержано библиотекой. Не логировать bot token в URL, initData, credentials и сырые личные ответы. Метрики p50/p95/p99 отдельно: UI feedback, API, callback ack, update→первый полезный ответ, job queue/result delivery, connect/read/pool failures, 429, reconnects, retries, pool saturation, worker lag. Проверять cold и warm отдельно: один быстрый warm-запрос не доказывает стабильность.

SLO под исправной внешней сетью и согласованным load profile: локальная реакция ≤100 мс; простое API p95 ≤500 мс; ack от получения update p95 ≤1 с; простая команда update→принятый Telegram ответ p95 ≤2 с; приём долгой job p95 ≤1 с. Считать долю успехов и ошибок тоже: быстрый отказ не выдать за быструю работу. Load profile до приёмки записать (пример стартового теста: 20 одновременных пользовательских действий плюс один активный long poll и фоновая job); это тестовый ориентир, не обещание ёмкости Selectel. Пользовательская сеть/Telegram доставка измеряются end-to-end отдельно от серверного SLO. Все превышения имеют известный bounded timeout и честное состояние, не обещание абсолютной мгновенности.

**9. Обязательная проверка отказов перед сдачей.** Повторные команды/inline buttons; cold start и первая отправка; после idle/разрыва keep-alive; callback при занятых LLM/пуле; getUpdates и sendMessage одновременно; 429 с retry_after; connect hang; read timeout после возможной отправки; временный DNS failure; рестарт worker между persist/dispatch; duplicate webhook; burst reminders; возвращение сети. Локальным fault injection смоделировать 20–30% неудачных новых connect и доказать bounded восстановление/отсутствие голодания и бизнес-дублей, не пытаться создавать потери на общем production-сервере. При сбое все SLO могут быть недостижимы, но сроки попыток/очереди ограничены, действия и результаты не исчезают.

К отчёту приложить конфиг транспорта/пулов, сравнение cold/warm p95 и ошибок, реальные клиентские проверки Telegram, fault-injection результаты и оставшиеся ограничения. Одного ESTAB в ss, отсутствия ошибки в коротком логе или фразы «на aiogram поэтому быстро» недостаточно. Дополнить статической/интеграционной проверкой, что клиенты создаются при startup, закрываются один раз и не пересоздаются на каждый вызов. Никаких реальных изменений api.telegram.org/hosts/сервера из этого ТЗ без отдельного поручения.

## 4. Авторизация и безопасность данных

Сервер проверяет подпись `initData` по актуальному алгоритму Telegram, давность auth_date, принадлежность боту и затем выдаёт ограниченную сессию. `initDataUnsafe` не является авторизацией. TTL входных данных — конфиг, рабочий старт 10 минут; сессия имеет отдельный срок и ротацию. Запретить доступ к чужим объектам по ID, включая файлы, выгрузки, deeplink и worker jobs. CSRF/CORS/cookie-политика под фактический deployment; не логировать initData и секреты.

Изолировать загрузки: MIME+сигнатура, лимит 20 MiB как инженерное ограничение MVP, лимиты распаковки DOCX/EPUB, защита от zip bomb/path traversal/HTML scripts, таймаут парсера. Не исполнять встроенный контент. Парсинг в sandbox/ограниченном worker. Ссылки источника не дают права серверу скачивать произвольные URL: импорт по URL не входит в MVP. Markdown/формулы рендерить с sanitization.

До передачи LLM — явное согласие с назначением и провайдером; сохранять версию согласия. Минимизировать контекст запроса. Загруженный текст и ответы — недоверенные данные, инструкции из них не могут запускать tools, платежи, внешние запросы или менять квоты. LLM не получает секретов. Политика хранения и удаления доступна пользователю. Детали применимых правовых требований проверить для выбранного оператора/юрисдикции перед публичным запуском.

Время хранить UTC, расписание интерпретировать в подтверждённом IANA timezone. День привычки хранить как local_date с использованным поясом: смена пояса не дублирует отметки задним числом. API не доверяет счётчикам клиента. Удаление материала не удаляет незаметно принятые знания: предупреждать и давать выбор, сохранять разрешённый provenance-фрагмент либо явно показывать отсутствие источника.

### 6.1. Сквозные user flows для реализации

1. Первый ручной путь: /start → D00 → D01 → D06 → D07 (если темы нет) → D09 create → D08 → D10 → D11/D12 → D13 → D03. Сохранены тема, знание и attempts; trial не начат, AI ledger пуст.
2. Импорт: D14 → D15 parse → D16 consent/estimate → reserve/trial transaction → D17 worker job → D18 review → commit selected → D08. Cancel/error возвращает по правилам job, а не повторяет LLM при каждом входе.
3. Повторение: уведомление/deeplink → D03/D10 → resume или create session → D11/D12 → D13. При закрытии сохраняется последнее подтверждённое действие; повтор ответа не меняет статистику дважды.
4. Привычка: D19 → D20 → необязательно D23 AI draft → D20 confirm → D21 → D22 occurrence → инициатор. ИИ-предложение не сохраняется как активная привычка без подтверждения.
5. Покупка из лимита: D30 → D27 → D28 invoice → successful_payment → entitlement → исходная форма. После покупки ИИ-операция требует нового подтверждения; исходный текст сохранён.
6. Конец периода: сервер переводит в Free → D29 → выбрать активный набор → D03. D32 export и чтение разрешены до выбора. Смена тарифа следует отдельному правилу раздела 11.
7. Восстановление: D00 читает серверное состояние → D03 с continue или D17 с текущей job. Ошибка сети не записывается как учебная ошибка; ошибка оплаты не запускает новый invoice без действия пользователя.

### 6.2. Первый экран D01: конверсионный лендинг

Реализовать маркетинговую страницу внутри Mini App перед основной рабочей областью при первом обычном входе. Полная композиция, job story и тексты — раздел 6.1 дизайнерского ТЗ. Структура обязательна: hero с ценностью → проблема/результат → локальное демо упражнения → три шага продукта → методика с научными источниками → привычки → триал и тарифы → FAQ → финальный CTA. Это часть MVP, не отдельная будущая внешняя страница.

Цель: квалифицированное начало триала или покупка и дальнейшее создание первого материала. Не считать просмотр/клик активацией. Статическая часть и демо не обращаются к LLM; не расходуют квоты, не создают attempt, series и mastery. Числа и условия тарифов приходят из того же versioned catalog, что D27; не хардкодить копию 499/1099 в независимом рекламном компоненте. Для неуспешной загрузки каталога — пояснение и retry, без показа устаревшей цены как гарантированной.

Маршрут первого входа: D00 auth/state → D01. Существующий пользователь не должен каждый день проходить лендинг: сохранять `landing_passed_at` при явном переходе к trial/purchase/manual/skip; это не то же самое, что первая завершённая активация. Входы с валидным целевым deeplink и восстановление незавершённой сессии имеют приоритет над лендингом. Повторный просмотр из D33 «О приложении» не обнуляет onboarding/entitlement; Back возвращает в D33. Нативная Back на стартовом D01 скрыта; системное закрытие Telegram доступно. Возврат из D27 к D01 восстанавливает scroll и выбранный блок.

Переходы:

1. `trial eligible` + «Попробовать ИИ бесплатно» → D06 с intent AI → выбрать/создать тему → D15 → D16. Только D16 запускает trial после явного подтверждения, с прежними ledger-инвариантами.
2. `trial used, paid inactive` → «Выбрать тариф» → D27; альтернативно бесплатное ручное создание и просмотр.
3. `trial active` или `paid active` → «Продолжить обучение» → D03; другие действия доступны из рабочего приложения.
4. «Выбрать Старт/Про» → D27 с validated selected_plan → D28. После server-confirmed purchase при landing intent → D06 AI для первого материала. При отмене → D27 с тем же планом; Back → тот же тарифный блок D01. Покупка не запускает импорт без согласия.
5. «Начать вручную бесплатно» → D06 manual; «Пока посмотреть» → D03. Оба доступны без оплаты и без trial.

Интерактивное демо — готовый небольшой набор prompt/answer/application-case, с кнопкой показа ответа и сбросом. Не хранить пользовательский демо-ответ в учебной статистике; возможная анонимизированная аналитика взаимодействия без содержимого ответа. Место в тарифе, consent и доступ пользователя не меняются. Нельзя запускать бесконечные генерации «ещё пример» без квот: примеры заранее подготовлены.

Научный контент поставлять с кодом/контентным конфигом, версия и дата проверки. Для каждого утверждения: short_claim, explanation, author/year, title, URL, limitation. Базовые источники: [Yang et al., 2021](https://pubmed.ncbi.nlm.nih.gov/33683913/) — учебные тестирования; [Cepeda et al., 2008](https://pubmed.ncbi.nlm.nih.gov/19076480/) — интервалы; [Pan & Rickard, 2018](https://pubmed.ncbi.nlm.nih.gov/29733621/) — перенос. Допустимые формулировки и границы — в дизайнерском ТЗ. Не давать LLM динамически сочинять научные обещания, отзывы, проценты улучшения или citations. Отображать рядом ограничение: исследованы методы, не эффективность BrainRecall. Внешний источник открывается по действию пользователя, возвращение сохраняет scroll/демо. Невозможность открыть статью не блокирует использование приложения.

Sticky CTA реализовать с учётом всех safe-area слоёв и reserved layout space; скрывать/менять при видимом hero/финальном CTA и открытой клавиатуре, не перекрывать FAQ/ссылки. Страница доступна с клавиатуры/screen reader; accordions имеют expanded state. Цена показывается в Stars/30 дней; не подставлять доход разработчика в рублях как цену для клиента. Отсутствуют выдуманное social proof и таймер «триал закончится», пока trial не начат.

Аналитика воронки: `landing_viewed` (version, entry, eligibility), `landing_section_viewed` (section, once/view), `landing_demo_started/completed`, `landing_science_opened`, `landing_cta_clicked` (placement, intent, selected_plan), `onboarding_started`, затем серверные `trial_started`, `import_completed`, `candidates_accepted`, `payment_confirmed`, `session_completed`. CTA-событие не равно conversion. Для отчёта: среди уникальных first landing viewers за период считать начала триала в 7 дней и первую оплату в 30 дней отдельно; полезная активация — принят хотя бы один элемент и завершена первая реальная сессия в 7 дней. Когорты без полного окна наблюдения отмечать отдельно. Продление не считать первой покупкой; trial→purchase и direct purchase различать. Параметры attribution/deeplink валидировать и не превращать в доверенные инструкции.

Дополнительная приёмка: новый пользователь видит объяснение пользы и три пути; клики/демо не начинают trial; научные ссылки и ограничения видны; обе цены совпадают с сервером; нельзя второй раз получить trial через повторный показ; оплата с лендинга выдаёт доступ только по серверу; отказ не стирает выбор; повторный обычный вход не навязывает рекламу; никакая аналитика не содержит текст книги/демо-ответа. Проверить iOS/Android с safe areas, маленький экран, тёмную тему, большой шрифт и медленную сеть.

## 7. Расписание и оценка обучения

Не использовать LLM для выбора срока повторения. Scheduler — отдельный versioned детерминированный модуль с входами outcome/assisted/elapsed/item state и выходом next_due/state. Начальное рабочее расписание для recall: успешные самостоятельные воспроизведения на новых днях → интервалы 1, 3, 7, 14, 30 дней, затем 60/120; это инженерная гипотеза, не научная универсальная норма. Ошибка → короткая повторная попытка после нескольких других заданий и due на следующий день. Частичный ответ/подсказка не увеличивает ступень; интервал не более дня до следующей независимой проверки. Успех в тот же день не считается новым независимым успехом. Замена модуля на проверенный адаптивный scheduler допустима с миграцией состояния и сохранением этих продуктовых инвариантов.

Хранить результат применения отдельно от recall: не объявлять перенос только за воспроизведение определения. Не маркировать «знает навсегда». Показатели памяти строить на отсроченных attempts, не на ответах сразу после просмотра. Точный числовой прогноз вероятности забывания не показывать без валидированной модели.

Проверка: нормализуемые точные ответы/числа/варианты — алгоритм; свободный текст — self-check по умолчанию, ИИ по явному выбору с показом квоты до отправки. Числовой ответ включает допустимую погрешность и единицы; нормализация не должна делать неправильную формулу правильной. Режим self-check требует сначала показать эталон, потом запросить оценку, а не считать клик «показать» успехом. AI grade по rubric с JSON schema, provenance и возможностью спора; неудачная проверка оставляет self-check.

Сессия: due раньше нового; пользовательский time budget; дневной cap нового на старте 5 элементов, редактируемый 0–20, дополнительные элементы добровольно. При большой просрочке показывать полный долг и посильную очередь, не фальсифицировать дедлайны и не генерировать бесконечные напоминания. Архив/пауза/readonly исключены. Временная пауза не удаляет историю.

Единственный источник правил общей серии, серий тем/привычек и достижений — раздел 7.1 ниже. Общая серия требует выполнения всего зафиксированного посильного дневного плана; прежнее правило «достаточно одной сессии или привычки при наличии невыполненного плана» отменено. Учебная правильность и регулярность считаются раздельно.

### 7.1. Контракт геймификации (обязательный MVP)

Объём и визуальные поверхности — раздел 7.1 дизайнерского ТЗ, D36–D38. Во всех тарифах бесплатно: общая серия за план, серии тем/привычек, personal best, календарь, milestones, короткое празднование и спокойный возврат. XP, рейтинги, персонажи и платное восстановление уже сброшенной серии не реализуются. Однодневная/недельная защита, бесплатная выдача и покупки Stars обязательны по разделу 7.2; прежний запрет платной заморозки отменён. LLM для этих расчётов не используется.

**Фиксируемый план:** DayPlan(user, local_date, timezone_snapshot, policy_version, required_items/occurrences, created_at, frozen_at). План строится на границе дня по данным, известным на эту границу; при остановке worker восстанавливается детерминированно из истории, включая дни без открытия приложения. Snapshot содержит ограниченную бюджетом очередь повторений и scheduled occurrences привычек. Остальная просрочка видна отдельно. До первого плана — дата активации первого реального знания/привычки, не /start/демо. Создание объектов в текущий день не добавляет неожиданные обязательства: они попадают в следующий план, сегодняшняя практика добровольна. Изменения приоритетов/объёма/паузы после формирования снимка действуют со следующего дня и не закрывают пропуски; удалённое ради соблюдения права на данные содержимое не сохранять в snapshot, оставить минимальное обезличенное состояние обязательства/причину отмены, без штрафа за техническую недоступность сервиса.

**Статус пользователя за день:**

- earned: выполнены все неотменённые обязательства и есть хотя бы одно реальное completed study unit/выполнение привычки. Успех ответа не обязателен. Minimum привычки равен выполнению; no_opportunity снимает только соответствующее обязательство, но само по себе не зарабатывает день.
- pending: день ещё идёт и есть невыполненное обязательство. UI показывает прошлую серию, текущий прогресс и остаток, не сбрасывает заранее.
- missed: граница дня прошла, обязательства остались невыполненными и доступная защита по разделу 7.2 не применена. Сбрасывает current до 0, не стирает историю/best.
- neutral: обязательств не было/все отменены по допустимой причине и нет выполненной практики. Не увеличивает current и не разрывает цепочку.
- Если обязательств нет, но есть добровольная завершённая реальная сессия/выполнение актуальной привычки — earned. Просмотр demo/карточки, импорт, покупка и создание пустого плана не являются практикой.

После earned увеличение один раз на local_date. Статус frozen — пропуск, защищённый по разделу 7.2: сохраняет цепочку без +1. Календарь хранит все статусы; число серии — количество earned между missed, а не длина календарного диапазона. Для темы применяется её часть DayPlan, для привычки — одна запланированная opportunity; no plan/pause/no opportunity нейтральны, skipped/неотмеченная завершившаяся opportunity — missed. В смешанной сессии фиксировать завершение частей тем отдельно. Best сохраняется как максимум корректной истории; текущая дата до закрытия может иметь earned или pending. Добровольные внеплановые отметки не увеличивают scheduled streak привычки, но могут дать реальный earned общей серии.

Модель: DayPlan/DayPlanUnit, DayOutcome (unique user/date/policy), StreakAggregate(scope_type user/topic/habit, scope_id, current, best, as_of, revision), AchievementGrant(unique user/scope/object/threshold), CelebrationInbox(id, grants[], seen_at), ReturnNotice(gap_id, scopes[], seen_at). User preferences дополнить achievement_effects_enabled. Данные локализуются при отображении, не сохранять русский текст достижения вместо code/parameters.

Источники — только canonical attempts и habit occurrences. Агрегаты вычисляются сервером, а не суммой кликов клиента. Транзакционно записать исходное событие, результат плана и уникальный grant; повтор webhook/submit/refresh не даёт новую награду. При multi-device параллельной записи один earned на дату. UI получает current/best/today_state/remaining/next_threshold/grants, не выводит их самостоятельно из видимого page списка.

Пороговые значения: 1, 3, 7, 14, 30, 60, 100, 180, 365; каждый порог на каждый scope/object выдаётся один раз за всё время. При пересчёте с прыжком через несколько порогов выдать все, но показать одно празднование с наибольшим и кратким списком остальных. Пропуск не отзывает уже полученный значок; исправление ошибочных исходных данных пересчитывает current/best и помечает недействительный grant corrected, без обвиняющей коммуникации. Создание/удаление новых объектов не переиздаёт старые grants.

Финализация missed на границе локального дня, не только при /start. Job reconciliation наверстывает пропущенные даты, безопасна при retry. Смена timezone вступает для DayPlan со следующей границы, уже существующий день и его deadline не переписывать; миграция пояса не создаёт два earned за одну и ту же временную практику. Смена языка никак не влияет на даты/серии. Сбой сервиса с недоступными обязательствами оформляется серверным нейтральным исключением с audit, не платной заморозкой.

D37 создаётся при новом фактическом разрыве существовавшей серии >0; дни без какой-либо начатой серии не создают уведомлений потери. При нескольких пропусках объединять gap и scopes. Открытие/закрытие, read/ack и празднование повторно не меняют counters. При начале практики из deeplink не ставить D37 поверх вопроса. D38 не автопоказывать после поздней server reconciliation до загрузки нужного контекста; новые достижения доступны в D36, при активном завершении — одно объединённое празднование. Haptic только однократно в активном пользовательском действии, не в background/webhook.

Безопасное исправление ошибочной отметки привычки возможно за последние 7 локальных дней, с audit и пересчётом зависимых дней; дату исправления не засчитывать за прошлую практику как новый сегодняшний earned. Пропущенное занятие задним числом не создаётся. Различать correction и новый activity event. После такого пересчёта не показывать фальшивый экран пропуска, который пользователь уже исправил; отображать итоговую canonical версию.

Обязательные проверки: earned → neutral → earned даёт 1 → 1 → 2; missed → earned даёт 0 → 1 при сохранённом best; pending сегодня не сбрасывает вчерашнюю серию; выполнена одна из двух привычек — общий план не earned; все no_opportunity без практики — neutral; неверные ответы при завершённой практике дают credit; смешанная сессия считает темы независимо; threshold 30 даётся один раз после refresh/двух клиентов; один шаг с несколькими milestones — один inbox; несколько дней без входа с due действительно прерывают серию; плановая пауза не исправляет вчерашний пропуск; timezone/DST/коррекция/удаление и restart worker не дублируют награды. Эти правила имеют приоритет над прежним кратким описанием серии.

### 7.2. Freeze ledger, выдача и Stars-товары

Продуктовый контракт полностью задан разделом 7.2 дизайнерского ТЗ, включая дневную/недельную защиту, кап 2 единицы, бесплатную награду каждые 7 earned и максимум 7 защищённых дат за rolling 30. Это исключение к прежнему запрету платных заморозок. Заморозки не расходуют ИИ и не являются подпиской.

Хранить FreezeLedger(user, entry_id, kind grant/purchase/consume/compensate, amount, source_id, source_type, local_date, created_at), RewardCycle(user, earned_total, last_processed_threshold), ProtectionInterval(user, start_date, end_date_exclusive, timezone_snapshot, order_id, status/reservation), ProtectedDate(user, local_date, source, protected_scopes[], policy_version), пользовательский freeze_auto_enabled (по умолчанию false). Баланс derived из ledger, unique source/grant/consume IDs. У бесплатной награды пороги lifetime earned_total 7,14,21…; начальный grant отдельно unique на первый earned. Порог при cap=2 пометить processed_without_grant, не оставлять очередь требований. Ledger хранит paid/free происхождение; при автоматическом расходе бесплатные первыми. Баланс не может стать отрицательным или штатно превышать 2, pending purchase резервирует свободное место.

Финализация дня транзакционна: определить earned/neutral/необходимость защиты по всем scopes → проверить активный недельный интервал и доступный cap дат → иначе проверить freeze_auto_enabled и дневной баланс → один consume на дату для всех нуждающихся scopes → frozen либо missed. Не расходовать при отсутствии сохраняемой цепочки или когда всё выполнено/нейтрально. Произошедший ранее confirmed purchase должен существовать до закрываемой границы дня; позднее получение webhook не даёт права искусственно спасать старый день по времени обработки. В спорном pending платеже использовать подтверждённые данные Telegram, не часы клиента; не обещать защиту до подтверждения. Restart/multi-worker не списывают вторую единицу. D37 создаётся только после этого решения, не для frozen.

Lifetime earned_total растёт один раз за подлинный зачёт общей серии, не от frozen/neutral/покупки. Коррекция исходных данных пересчитывает право на ещё не обработанные grants; уже использованные награды не превращают баланс в долг, не дублировать grant после undo/replay одного порога. Выполненную впоследствии дату не оставлять одновременно earned и frozen: исключить двойной credit; исправление отметок аудируется, покупки и награды повторно не возникают. Излишне потраченную бесплатную единицу компенсировать лишь до cap; если ошибочно потрачена платная и места нет — возврат конкретной разовой покупки через поддержку, не скрытое превышение склада.

Rolling 30 учитывать по защищённым local dates со snapshot timezone, а для нового недельного интервала также все зарезервированные будущие даты: нельзя через несколько предварительных покупок превысить 7 в любом окне 30 дней. Неделя — 7 последовательных календарных дат, не 168 часов (DST), старт не ранее завтра и не далее 30 дней, один действующий/предстоящий интервал, без overlap. Резерв 7 дат остаётся на весь купленный интервал даже при добровольной практике; пользователь заранее об этом уведомлён. Однодневный stock можно хранить, но его использование не обходит reservation/cap. Plan pause остаётся бесплатной отдельной операцией; не заменять её платной защитой.

Платёжный каталог дополнить `freeze_day` и `freeze_week` с integer XTR price и version. Конкретные цены — deploy config владельца, отсутствующие цены означают недоступность покупки, а не 0 Stars. `Payment.product_type` различает plan/freeze_day/freeze_week; один pending order пользователя блокирует повторные клики и резервирует capacity/interval. Для защиты — обычный одноразовый invoice, **без subscription_period**; никаких автопокупок за Stars. D28 для этого товара возвращает в D39. Доставлять только по подтверждённому successful_payment, не по invoiceClosed. [Официальный порядок Stars-платежа](https://core.telegram.org/bots/payments-stars).

Pre-checkout проверяет актуальную цену, user/order, баланс + pending slots <=2, отсутствие второго интервала, cap дат и начало периода. Пока pending, бесплатный grant проверяет зарезервированное место; недоставленный/expired reservation освобождается по reconciliation, но оплаченный поздний webhook нельзя терять: либо доставить при допустимом capacity/интервале, либо выполнить полный возврат, явно сообщив результат. Выручка/расход API подписки и freeze purchases учитываются раздельно; покупка защиты не выдаёт тариф и не обнуляет квоты. Refund неиспользованного товара отзывает его единицу/интервал; использованный оплаченный товар — отдельный support flow без отрицательного баланса и без тихого удаления учебной истории. Неделю не продлевать автоматически.

API: получить balance/grant_progress/rolling_capacity/active_interval/prices, toggle auto, проверить interval eligibility, создать order, прочитать order/delivery. Ни один из этих запросов кроме подтверждённой delivery/финализации/grant не меняет баланс. Серверные события freeze_granted/skipped_at_cap/purchased/consumed, week_protection_scheduled, purchase_refunded; UI не генерирует факт выдачи. Free/Trial/paid имеют одинаковые правила выдачи.

Проверки: первый grant один раз; 7 earned при свободном слоте даёт +1; 21 earned при 2/2 не создаёт скрытый долг; после расхода нет немедленной выдачи за старые пороги; neutral/frozen не увеличивают earned_total; параллельные grant/purchase не превышают 2; все scopes одной даты расходуют 1; неделя не расходует дневной stock; cap rolling с overlap/таймзоной/DST; неуспешный платёж не даёт protection; pending через полночь/поздний webhook/refund/restart не дублируют delivery; бесплатная плановая пауза остаётся доступной.

## 8. Привычки и уведомления

Шаблон: после/если X → действие Y → минимум Z; запасной план при препятствии; сделать сигнал очевидным, действие привлекательным/простым, награду доступной. Для замены нежелательного действия — сигнал, потребность, замена и изменение среды. Никаких денежных штрафов по умолчанию и обещаний сроков автоматизации.

Occurrence outcomes: minimum_done/full_done/skipped/no_opportunity; planned_pause задаётся расписанием. Один пользователь/привычка/плановая возможность — одна запись, повторный тап идемпотентен. Незапланированные действия можно записать отдельно, без подмены выполнения задним числом. Частоты MVP — выбранные дни недели и одно окно на день; несколько повторов в день/геолокационные триггеры вне MVP.

Бот /start, открыть Mini App, /help, /paysupport. Напоминания только после разрешения/реальной возможности писать пользователю; не обещать отправку при blocked. Один дневной digest и необязательные настроенные окна привычек; объединять совпавшее. Дедупликация user/window/date/type, quiet hours, DST, изменение timezone, retries с backoff и обработка 429/403. Не отправлять накопленную пачку после downtime: одно актуальное сообщение. Ссылка ведёт в приложение с серверной проверкой цели и прав.

## 9. Импорт, ИИ и контроль качества

Конвейер: upload → parse → token count → confirm/reserve → queue → extract → generate exercises → validate → review → commit selected. Для разметки сохранять страницы PDF/абзацы DOCX/главы EPUB/offset текста. Нельзя выдумывать номера страниц, когда формат их не содержит. До LLM показать цель и расход. Поддерживаемый файл ограничен 100 000 исходных токенов и 20 MiB; короткие файлы суммируются пропорционально, не округляются по 10 000.

Токенизатор выбранной модели или подтверждённый provider counting endpoint. Если точного токенизатора нет, не выдавать символы/4 за точный расход: использовать явно отмеченную оценку с запасом, до запуска согласовывать максимальный резерв, при завершении сверять и освобождать лишнее. Платформенные overhead input токены не вычитать из обещанной квоты исходного текста. Внутренняя provider usage и пользовательская квота — разные счётчики.

Выделять факты, понятия, формулы, условия применимости, мнение автора, гипотезы; связывать с фрагментами. Проверять JSON, длины, полноту эталона, валидность anchors, дубли, отсутствие явного противоречия исходному фрагменту. Не обещать фактчекинг книги внешними источниками. Не показывать сырые chain-of-thought. Непринятые кандидаты не становятся активными элементами. Review может продолжаться после истечения тарифа; activation подчиняется текущему лимиту, черновики остаются читаемыми.

Бюджетный ориентир на 10 000 исходных токенов из модели экономики: 36 000 input / 8 000 output на все проходы; не SLA провайдера и не гарантированное число задач. Для каждого типа вызова задать max output, prompt version, timeout, до 2 автоматических повторов только для retryable ошибок; затраты неудач несёт сервис в рамках резерва. При выходе за бюджет остановить job безопасно, восстановить клиентский неиспользованный резерв, показать понятное состояние. Платный кейс/объяснение генерируется по запросу и сохраняется; повторный просмотр не списывается.

Длинная job переживает выход из WebView и рестарт worker. Stage checkpoints, lease/heartbeat, повторяемые шаги и дедупликация. Cancel до старта освобождает весь резерв; после старта завершает текущий безопасный шаг и возвращает неиспользованную часть; до подтверждения отмены объяснить, что уже обработанный объём может быть учтён. Ошибка сервиса не расходует пользовательскую квоту за невыданный результат, реальный API cost всё равно логируется. Возврат квоты не является возвратом Stars.

Все квоты на аккаунт, не тему. Ручное создание, self-check, показы сохранённых упражнений и алгоритмическое расписание не вызывают LLM. Источник истины — серверный versioned plan config. Активность ограничивается и темами, и элементами; 500 элементов внутри 4 тем не обходят ограничение Free. Архив не расходует active quota, но имеет инженерный storage abuse limit с отдельным понятным сообщением, не скрытую платную квоту.

Quota ledger: в одной транзакции проверить остаток и reserve; operation_id уникален; commit actual usage либо release/refund. Нельзя read-then-write без блокировки: два одновременных запроса не должны потратить один остаток. Повтор клиента возвращает ту же job/result. Usage переносится с конкретным period_id: job, завершённая после границы, финализирует старый резерв, а не списывает новый период. Старые незавершённые резервы имеют TTL/reconciliation и не зависают навсегда.

Платные квоты выдавать на подтверждённый оплаченный период; остатки не переносить. Покупка во время trial немедленно включает платный доступ и прекращает trial; остатки не суммируются. Плановые изменения тарифа действуют со следующего периода. При окончании доступа — Free; сверхлимитные объекты read-only, пользователь выбирает активный набор D29. До выбора сверхлимитный каталог не запускает обучение; не удалять данные и не блокировать экспорт. Архивирование не обнуляет ранее потраченный AI usage.

## 11. Stars и жизненный цикл оплаты

Использовать нативные платежи за цифровые услуги: [Stars payments](https://core.telegram.org/bots/payments-stars), [createInvoiceLink](https://core.telegram.org/bots/api#createinvoicelink), [SuccessfulPayment](https://core.telegram.org/bots/api#successfulpayment). Currency XTR, целое число Stars, один price item. Рабочий режим — recurring на 2 592 000 секунд. Пользователь видит «каждые 30 дней», дату следующего списания и кнопку отмены. Триал без платежа и без автоматического перехода на платный.

Порядок: сервер создаёт order с plan version/ценой → подписанный payload → invoice link → openInvoice → pre_checkout_query проверяет цену, пользователя, order и право на покупку → подтверждённый successful_payment выдаёт entitlement. pre_checkout отвечать в установленный Bot API срок (10 секунд). Подтверждение клиента/invoiceClosed само по себе не выдаёт доступ. Pending может длиться дольше жизни WebView; повторный вход читает order с сервера.

Webhook защищён secret token, unique update_id, unique telegram_payment_charge_id, transactional upsert. Сохранить subscription expiration/charge id и поддержать повторную доставку, поздний платёж, refund и reconciliation. Не сбрасывать квоты при каждом повторном webhook. Две вкладки не создают две активные подписки: блокировка на пользователя, один pending order, recheck в pre_checkout. Telegram технически допускает несколько подписок, поэтому ограничение нужно реализовать самим. Не отменять оплату уже после успешного списания молча: оплаченный duplicate обработать как инцидент и возврат/сверку по понятному правилу.

Отмена продления: сервер вызывает [editUserStarSubscription](https://core.telegram.org/bots/api#edituserstarsubscription), подтверждает результат; доступ сохраняется до конца оплаченного срока. Возобновление — только в поддерживаемом статусе с подтверждением пользователя. При downgrade/upgrade со следующего периода остановить старое продление и сохранить desired plan. В дату окончания предложить оплатить новый тариф новым invoice: автоматический перенос согласия на другую цену не реализовывать. До оплаты новый доступ не выдаётся; при неуспехе Free. Явно сообщить, что смена запланирована и потребует подтверждения новой оплаты, чтобы не обещать автоматическую миграцию.

Refund через [refundStarPayment](https://core.telegram.org/bots/api#refundstarpayment); сверка статуса в audit и прекращение соответствующего entitlement по политике возврата. Удаление аккаунта должно сначала попытаться остановить продление и предупредить пользователя при невозможности; не продолжать скрытое списание. /paysupport и действительный контакт владельца обязательны. Налоги/юридические документы не выдумывать, настроить после выбора оператором правил. Нативные topics в private chat не включать без отдельного решения: они не нужны этому MVP.

## 13. Экспорт, удаление, эксплуатация

Экспорт: UTF-8 JSON с версией схемы, темами, знаниями, упражнениями, доступными источниками, привычками и историей; читаемый Markdown дополнительно. Асинхронный job; ссылка на скачивание ограничена владельцем и коротким сроком, не публичный постоянный URL. Платёжные секреты и внутренние промпты не экспортируются. Квоты/состояния в экспорт включить как справочные, не возможность восстановить платные права произвольным импортом. Обратный импорт архива вне MVP.

Удаление: подтверждение, отмена продления, запрет новых jobs, отмена ожидающих, удаление активных пользовательских данных/файлов и cache. Срок для рабочих данных — до 7 дней как целевое внутреннее SLA; резервные копии с ротацией до 30 дней, если политика и выбранный режим позволяют. Платёжный аудит с обязательным сроком хранения изолирован, минимизирован и объяснён. Не объявлять полное удаление до выполнения jobs; внешнее хранение провайдера отражать в политике, не обещать неподтверждённого удаления у него.

Метрики: API latency/error rate, queue age, job retries, disk/DB, reminder failures, фактический cost AI per operation/plan/period, reserved quota drift, webhook lag, payment mismatch. Глобальный AI budget kill switch останавливает новые ИИ-запросы с объяснением, оставляет ручные функции. Хранить prompt/provider model version, tokens и cost, без сырых секретов. Backup restore провести до запуска. При оценке нагрузки не обещать «сервер выдержит N пользователей» без измерения реальных сессий и очередей.

### 16.3. Реестр задач продвижения и измерение

Для каждой площадки: применимость/N/A с причиной, URL официальных требований, checked_at, ответственный, материалы/версия, статус и дата подачи, замечания, ссылка на опубликованную карточку, следующий шаг. Не подменять этот реестр списком «уже опубликовано» без evidence.

Через общий analytics facade измерять source/campaign → landing → начало onboarding/подключения → первый полезный результат → повторное использование → оплата/удержание; ссылки с безопасной attribution, без токенов и PII. Для MCP добавлять install attempt/success, успешный разрешённый tool call и uninstall/error, не считать скачивания npm реальными людьми. Для Telegram — app open и первый результат, а не одни /start. Если проводится реферальный эксперимент — только добровольное приглашение без чтения адресной книги/рассылки без согласия.

Основные решения — по квалифицированным активациям, времени до результата, удержанию/платной конверсии и затратам поддержки, не по одним звёздам GitHub. Не накручивать stars/downloads, не гонять CI ради популярности, не добавлять нерелевантные topics/aliases и спам-посты. Бейджи и E2EE/security statements только при подтверждённом основании. Проверять правила саморекламы и раскрывать авторство; конкретные рекламные/юридические условия и платные размещения согласовать отдельно.
